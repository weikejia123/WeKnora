3记忆系统：核心设计（中）

记忆系统的价值在于解决「长期记忆对知识库产品」的四大痛点，以下是针对痛点展开的关键设计决策。

3.1 要解决的四大痛点（设计出发点）

痛点一：记忆污染提示词
记忆条目会注入每个会话的系统提示词。若内容过长或含敏感信息，会稀释上下文、甚至把密钥送进模型。
痛点二：错误记忆静默污染
后台抽取可能推断出错误事实（如误判用户身份、偏好）。错误记忆一旦进入上下文，会持续误导后续回答。
痛点三：记忆与知识库脱节
记忆只进提示词，无法影响检索结果，在知识库产品里价值有限；用户常用的文档不被记忆偏好牵引。
痛点四：记忆膨胀与成本
长期积累下记忆条目会无限增长，常驻 block 与抽取调用都会带来持续成本，且无关记忆会干扰判断。

3.2 关键设计决策（逐条：为什么这么设计）

设计决策核心做法为什么这样设计（针对痛点）
① 双时态替代（bi-temporal supersede） 冲突记忆用「替代」而非「删除」：旧条目保留内容，标记 invalid_at + superseded_by，只在实际被忘记时才物理删除。 既保留「上个月这个事实是什么」，又能让记忆管理器解释「发生了什么变化」，避免冲突记忆静默覆盖。
② 待确认人工确认（pending，永不注入） 后台抽取出的推断条目进入 pending 状态，永不注入提示词；仅用户确认后才启用，确认时同事务替换旧条目。 直接针对「错误记忆静默污染」：猜错身份/偏好是记忆类产品的最大信任风险，必须由人把关。
③ 敏感信息自动脱敏（RedactSensitive） 写入前用 sensitivePatterns 过滤凭据、身份证、银行卡、手机号、高熵串等，替换为「【已隐藏】」占位。 记忆会注入系统提示词，把密钥/身份信息写进去等于把敏感数据反复送进模型，属于安全红线。
④ 记忆与检索联动（retrieval conditioning） 记忆不仅进提示词，还作为 query 改写与文档排序信号：记忆里的兴趣/主题影响检索改写，文档亲和表让「用户常用文档」获得 rerank 加权。 针对「记忆与知识库脱节」：让记忆在知识库产品里真正产生价值，这是记忆类产品在 KB 场景的差异化关键。
⑤ 向量检索下沉到数据库（pgvector，无近似索引） 记忆向量写入独立表 memory_item_embeddings，由数据库按余弦距离排序（::halfvec <=>），不做近似索引。 单主体向量量小（最多数千行），精确排序既正确又快；且把相似度计算放在 DB 内，避免把向量传回应用再打分。
⑥ 三档预算控制（resident / recall / search） 常驻 block、查询匹配 recall、按需 search 分别设 rune 预算（900 / 600 / 2000）与条数上限（5 / 5 / 20）。 针对「记忆膨胀与成本」：常驻上下文每轮都付成本，预算控制避免无关记忆稀释提示词，search 比 recall 更宽松（按需付费）。
⑦ 主题解析与兴趣提升（阈值 + 字符 bigram） 主题先计数（memory_topic_stats），达到阈值（默认 3 次）才提升为长期兴趣；用字符 bigram 做模糊匹配，且只做「更具体」的标签提升避免泛化。 针对「记忆膨胀」：单一问题不会产生记忆，反复出现的主题才值得沉淀；避免把每个问题都记成长期兴趣。
⑧ 无账号身份记忆管理 IM 用户、嵌入访客、API 外部用户可能无登录账号；空间 Admin/Owner 可管理这些匿名身份的记忆（列表 / 确认 / 拒绝 / 清空 / 开关）。 覆盖边界场景：记忆按主体隔离，必须有「无账号身份」的管理通道，否则这些用户的记忆无法被访问或清理。
⑨ 写代次 fencing + 一致性保障 清空等写操作切换「写入代次」，旧代次写入被拒绝；配套一致性测试、并发竞态测试、迁移版本校验。 针对并发安全：后台抽取与用户操作并发时，必须保证不会出现旧提取覆盖新记忆、或清空后又被写回的情况。

3.3 与主流记忆方案的设计对比

设计对比要点（证据：源码注释明确对标 mem0 / Graphiti）： extract.go 注释明确「mem0 shows 10 by vector similarity, Graphiti at most 15 per entity」——说明抽取候选数量对标行业方案； memory.go 注释「Graphiti skips fuzzy matching for low-entropy names」「Graphiti keeps the more specific node when collapsing duplicates」——说明主题解析/冲突处理对标 Graphiti 的实体解析思路。 这证明记忆系统的设计有明确的行业对标与收敛，而非自创路径。
维度WeKnora（wkj-dev）主流记忆方案（mem0 / Graphiti / Zep / LangMem）
记忆与知识库联动 强：记忆反哺检索改写与文档排序（retrieval conditioning + affinity rerank） 多为「记忆仅进提示词」，与知识库检索脱节
冲突与一致性 强：双时态替代 + 拒绝抑制 + 写代次 fencing + 一致性/竞态测试 多以删除或简单覆盖处理冲突
人工确认（信任） 强：推断条目 pending 永不注入，确认才启用 多为全自动抽取，无人工确认环节
安全脱敏 强：写入前敏感信息自动过滤（凭据/身份/银行卡/手机号） 多未针对「记忆注入提示词」做系统级脱敏
向量检索方式 稳定：DB 内精确排序（pgvector），无近似索引，针对单主体小规模优化 多为应用内打分或近似索引
记忆与知识库融合 强：记忆 → 文档组织（主题提升 / 文档偏好 / Wiki 高亮）双向联动 多为独立记忆引擎，与知识库组织不融合

4.4 记忆迁移演进（展示设计的演进与稳健性）

迁移内容设计意图
000084_memory 创建 memory_subjects / memory_items / memory_tombstones / memory_topic_stats / memory_doc_affinity / memory_item_embeddings，并在 tenants 加 memory_config、messages 加 used_memories。 定义基础数据模型与双时态替代、拒绝抑制、主题计数、文档亲和、向量独立表等核心结构。

Embedding 模型 API 必须 没有 Embedding API 完全无法入库与检索，比 LLM 更底层；仓库无任何本地模型文件，必须远程自备。 内网自备 Embedding 服务（OpenAI 兼容）
LLM（KnowledgeQA）API 必须 问答 / 摘要 / Agent 全部依赖；用于抽取与回答。 内网自备 LLM 服务（OpenAI 兼容）
5 个核心离线镜像 必须 app / ui / docreader / ParadeDB / redis；docreader 最大（含 LibreOffice + Playwright + OpenJDK）。 docker save/load 搬运或私有 registry
基础中间件 必须 Postgres（ParadeDB，含 pgvector）+ Redis，随镜像自带，无需额外准备。 随镜像部署
Rerank / VLM / ASR API 可选 分别影响检索质量 / 扫描件识别 / 音频转写；不配置则功能降级但不阻断。 按需接入
处理默认出网配置 必须 默认有 8 处会主动出网的行为（Ollama、网络搜索、数据源同步、Langfuse、对象存储、外部解析、沙箱、云托管模型），内网需逐个关闭或替代。 按 4.4 处置表逐项处理
证书信任（如需浏览器 / WSS） 可选 接入层为自签 CA；浏览器访问需信任 CA（Mac 用 security add-trusted-cert）。 按需导入 CA
生产压测与安全验证 必须 记忆涉及长期数据与模型调用，需做安全（脱敏/权限/审计）与性能（抽取并发、检索）压测。 上线前专项压测

5.3 适用场景

场景匹配度说明
企业知识库 + 多空间 RBAC + 长期记忆（私有化内网） 强 多空间隔离、四级角色、审计、记忆按主体隔离，满足私有化合规与多用户管理需求。
「文档既问答、又 Agent、又自动沉淀 Wiki + 记忆 + 国内 IM」一体化 强 三模式合一 + 自动 Wiki + 记忆 + IM 渠道（企微/飞书/钉钉/QQBot 等），是国内企业场景最贴合的一体化选择。
需要长期记忆跨会话、记忆召回个性化检索、记忆与知识库联动 强 记忆反哺检索与文档组织，是知识库产品里记忆最实际的落地形态。
需要记忆管理（确认 / 拒绝 / 整理 / 导出 / 无账号身份管理） 强 管理接口覆盖个人与匿名身份（IM/嵌入/API 用户），边界完整。
深度版面解析（复杂表格 / 扫描件行列语义） 弱 深度解析不及 RAGFlow；如需最强解析，应选 RAGFlow 或在其上叠加解析能力。
可视化工作流编排 / 动态插件 弱 无可视化工作流、无 Go 动态插件；适合 Agent 编排，不适合工作流可视化需求。

5.4 边界与风险

风险 / 边界影响缓解方式
默认检索向量库为逻辑隔离（Postgres 共用向量表） 多领域若共用默认 ParadeDB 引擎，向量层只有逻辑隔离，数据物理仍混表 多领域物理隔离需接入 Qdrant / Milvus / ES / OpenSearch / Weaviate / Doris / 腾讯云 VectorDB 之一，按 KB 绑定 store
记忆抽取依赖 LLM 归纳，质量受模型与提示词约束 抽取质量影响长期记忆准确性 开启「仅明确记住」模式先验证；用 pending 人工确认把关；可配置提取指令与抽取模型
自动抽取有模型调用成本 高频会话会持续产生抽取调用，成本与数据增长 配置 extract_delay_seconds / extract_min_interval_seconds 控制频率；用 interest_threshold 控制兴趣沉淀
社区规模小、生态弱、无动态插件 后续扩展（新向量库/协议模型）需改代码重建镜像，迭代速度慢 优先用 OpenAI 兼容协议零代码接入；扩展需求提前评估改代码成本
深度版面解析能力不足 复杂表格 / 扫描件解析质量受限，影响入库与检索 如需强解析，叠加 MinerU / PaddleOCR-VL 等外部解析服务（配置即用）
生产前必做：在完成前置条件搭建后，建议先以「少量数据 + 小空间」做一次记忆功能冒烟（入库 → 抽取 → 召回 → 检索联动 → 冲突/拒绝/整理）， 再逐步扩大规模；记忆涉及长期数据，建议在正式生产前做一次数据备份（沿用数据安全方案）。

6行业领先性评估（对比层）

记忆系统是否处于业内领先？从「领先点」与「不领先处」两个维度，结合设计对比给出判断。

6.1 领先点（带证据）

记忆与检索联动（领先）
记忆不仅进提示词，还作为 query 改写与文档排序信号（retrieval conditioning + affinity rerank），让记忆在知识库产品里真正产生价值，多数记忆方案只做「记忆进提示词」。
冲突与一致性保障（领先）
双时态替代 + 拒绝抑制（tombstone）+ 写代次 fencing + 一致性/竞态测试，工程严谨度高于多数记忆方案（多为删除或简单覆盖）。
人工确认与信任（领先）
推断条目 pending 永不注入提示词，确认才启用——直接针对记忆类产品最大的信任风险（错误记忆静默污染），是人审把关的成熟设计。
安全脱敏（领先）
写入前用敏感模式过滤凭据、身份证、银行卡、手机号、高熵串，替换为占位——记忆会注入系统提示词，这一系统级安全设计很细。

6.2 记忆系统领先度评分（设计维度）

6.3 不领先处（需说清）

不领先维度说明
独立记忆引擎 记忆系统是「知识库平台的附加能力」，并非独立的记忆引擎（如 mem0 / Graphiti 是纯记忆引擎）；其领先在「与知识库融合」，而非记忆算法本身。
纯记忆算法能力 主题解析 / 兴趣提升依赖「阈值 + 字符 bigram」匹配，复杂语义主题的自动归纳能力弱于专用记忆引擎。
深度版面解析 复杂表格 / 扫描件深度解析不及 RAGFlow，属于项目整体短板，非记忆系统特有。
公开基准对比数据 缺乏公开的记忆质量基准对比数据，领先性判断主要基于源码设计对标，建议用真实业务样本做对照验证。
领先性结论：记忆系统在「与知识库融合 / 冲突与一致性 / 人工确认 / 安全脱敏」四个方向处于行业领先水平， 属于「融合型记忆设计」的领先实现；但不领先于纯记忆引擎与深度版面解析。选型时应结合业务诉求判断： 若核心诉求是「知识库内个性化记忆与检索联动」，WeKnora 记忆系统是领先选择；若核心诉求是「独立记忆引擎的算法能力」或「最强深度解析」，应选对应专用方案。

7.2 落地路线（分阶段）

阶段目标关键动作
阶段一
前置搭建		 满足生产前置条件 自备 Embedding + LLM API；5 个离线镜像 save/load 或私有 registry；逐项关闭/替代 8 处默认出网配置；按需导入 CA。
阶段二
记忆启航		 开启记忆并验证基础链路 标准版 Compose 部署；空间开启记忆（先 explicit_only 验证，再 auto）；配置抽取模型与延迟/间隔参数；做少量数据冒烟（入库→抽取→召回→检索）。
阶段三
检索联动		 让记忆真正影响检索与文档组织 开启检索条件化与文档亲和；配置向量模型与检索个性化；验证记忆偏好对检索排序与文档组织的实际影响。
阶段四
多领域与治理		 多空间 / 多身份治理 按领域建 Tenant；多领域物理隔离需更换向量库（Qdrant/Milvus 等）；完善 RBAC、审计、记忆管理（确认/拒绝/整理/导出）。
阶段五
安全与运维		 生产安全与稳定性验证 做记忆相关安全（脱敏/权限/审计）与性能（抽取并发、检索）压测；建立数据备份（记忆属长期数据）；固化生产部署脚本与巡检。

7.3 风险提示

重点风险：① 记忆涉及长期数据，抽取质量依赖 LLM，建议先 explicit_only 验证再 auto，并用 pending 人工确认把关； ② 多领域物理隔离需更换向量库，默认 Postgres 引擎只能逻辑隔离； ③ 自动抽取有模型调用成本，需用 extract_min_interval_seconds 等参数控制频率； ④ 社区规模小，扩展需求（新向量库/协议模型）需提前评估改代码成本。
总结：WeKnora（wkj-dev）工程成熟度达到生产可交付水平，其长期记忆系统是「知识库内融合型」的领先设计， 在融合、一致性、信任、安全维度具备行业优势；可进入生产，适用企业私有化知识库 + 长期记忆场景， 落地时按「前置搭建 → 记忆启航 → 检索联动 → 多领域治理 → 安全运维」分阶段推进即可。
