## 0. 一句话结论

**这个库的消费模式是"跨省跨年度的聚合分析"，不是"事实查找"；分块的正确原子单元是"审计问题条目"而非等长文本段。但实测显示问题至少三层叠加（解析噪声 / 切分边界 / 无元数据），只调分块参数解决不了。**

---

## 1. 实测基线（2026-09-27，API 全库扫描）

库配置：`strategy=auto`，parent-child 开启（parent 4096 / child 384），overlap 200，分隔符 `\n\n→\n→。→！→？→;→；`；PDF→mineru，html/docx→anydoc；auto_tag 开（max 10）。

全库 100 文档（50 HTML + 50 PDF）扫描结果：

| # | 现象 | 证据 | 归层 |
|---|------|------|------|
| 1 | 所有 chunk 均长 ≈300 字、上限 384 | 全库无一例外 | 分块层（child 粒度的设计值，非 bug） |
| 2 | HTML 导航/页脚污染，正文可能整体丢失 | 湖南-2024审计工作报告.html 仅 5 块，全部是导航菜单、面包屑、页脚（"主办单位：湖南省审计厅…"），**正文一块没有** | **解析层** |
| 3 | PDF 解析噪声入块且跨块断裂 | 辽宁-2025附件01 chunk3 = `<small><span class="docvortex-page-footnote"...`，chunk4 开头 = `</span></small>` | **解析层** + 分块层 |
| 4 | 超短噪声块 | 多个 PDF 最短块 9~30 字符（页码、脚注残片）；广西-2025附件01 均长仅 156 | 分块层（无后过滤） |
| 5 | 同内容重复入库 | 青海审计报告"图片型"与"正文图合并"分块统计完全一致（51 块/均 299） | 库管理 |
| 6 | 条目被切断 | "一是…；二是…"级发现被按段落/字数切到相邻两块，后半块脱离定性语 | 分块层 |

**判断准则：先分层，再归因。** 三层的责任边界：解析噪声是分块的前提污染（块里是垃圾，怎么切都是垃圾）；切分边界决定条目完整性；元数据决定聚合检索的可能性。三者互相独立，需分别治理。

## 2. 消费模式重定义（本方案的地基）

用户的真实用法（原话归纳）：

> 以"财政软件公司老板"视角，从各省审计问题中**找商机、排优先级、估人天成本、判断技术可解决占比、分析根因**，并按"全国政策方向 × 各省财政厅长视角"两个维度输出。

这不是"青海 2024 年惠农补贴发现了什么问题"式的事实查找，而是**跨文档聚合分析**。两者的分块需求完全不同：

| 维度 | 事实查找（WeKnora 默认假设） | 聚合分析（本库真实消费） |
|------|------------------------------|--------------------------|
| 检索单元价值 | 与 query 语义最像的段落 | 一条**结构完整**的问题条目 |
| 召回形态 | top-k 相似 | **跨省、跨年度、按问题类型全集** |
| 关键依赖 | 向量相似度 | 元数据过滤 + 条目结构化 + agent 综合 |
| 块内上下文 | 够用即可 | 必须自带"省/年/板块"面包屑，否则单块无法独立解读 |

**推论：默认的"等长子块 + 向量 top-k"对这个库是错配的。** 384 字子块按段落切断条目，且不带省份/年度元数据，聚合类问题的召回既不完整也不可过滤。

## 3. 分块方案：问题条目块 + 面包屑 + 结构化元数据

### 3.1 目标规格

| 层级 | 单元 | 粒度 | 说明 |
|------|------|------|------|
| 文档级 | 报告摘要块 | 1 块/文档 | 已有（knowledge summary/gist），作宏观检索入口，不动 |
| 父块 | 报告小节 | `（一）`级小节，≤4096 字 | 保持 parent-child 架构，parent 就是小节 |
| **子块** | **审计问题条目** | "一是/二是"级发现 + 其定性句，300~800 字 | **核心改动**：边界对齐条目，不对齐段落/字数 |
| 元数据 | 每块附加 | 省 / 年度 / 报告类型 / 板块 / 问题类型 / 金额提及 / 被审计对象 | 聚合检索的过滤与统计维度 |

子块正文前强制拼面包屑（WeKnora 的 `ContextHeader` 机制已支持，`internal/infrastructure/chunker/strategy.go` 的 `mergeBreadcrumbs`）：

```
【青海】【2024年度】【审计工作报告】二、重大政策落实审计情况 > （二）乡村全面振兴审计情况
一是部分县惠农补贴发放不及时，涉及资金 XXX 万元。……
```

无面包屑的条目块在"各省债务问题横向对比"场景下无法独立解读——这是聚合分析与事实查找最大的分野。

### 3.2 条目边界识别规则（审计报告文体特有）

判断准则：**利用公文的强模式，不发明通用规则**。审计报告结构高度可预测：

| 模式 | 形态 | 动作 |
|------|------|------|
| 板块标题 | `一、二、三、` 或 MinerU 输出的 `## ` | 父块边界 + 面包屑入栈 |
| 小节标题 | `（一）（二）` | 子块组边界 + 面包屑入栈 |
| 条目序号 | `一是…；二是…` / `1. 2.` / `（1）` | **子块边界**；条目与其定性引导句（"发现的主要问题："）同块 |
| 金额信号 | `XX 万元/亿元` | 触发元数据字段 `金额提及`，不切分 |
| 序数词形态 | `（一）`既是小节又是条目序号 | 按**嵌套深度**区分：跟在 `一、` 后为小节，跟在条目叙述内为条目 |

例外：图解页/一图读懂类 HTML 无条目结构 → 降级为文档摘要块，不做条目切分；纯表格附件 → 保持表格块完整（一行一事务），禁止按字数切断表格。

### 3.3 解析层前置治理（不做这个，切分无意义）

| 动作 | 对象 | 方式 |
|------|------|------|
| HTML 正文剥离 | 政府 HTML（导航/面包屑/页脚占实测块的大头） | 上传前预处理：正文抽取转纯 markdown 再入库（B 路径，见 §5） |
| 脚注/页码残片过滤 | mineru 输出中的 `docvortex-page-footnote` HTML 片段 | 分块前正则剔除；(`<small>` 级标签不参与切分 |
| 超短块合并 | <50 字符的块 | 并入前块，不独立成块 |
| 重复文档去重 | 图片型 vs 正文图合并 | 入库时按内容指纹检测，人工确认后二选一 |

## 4. 分块如何服务四个输出维度

| 输出维度 | 依赖什么 | 本方案供给 |
|----------|----------|------------|
| 商机优先级排序 | 同类问题跨省出现频次 + 金额规模 | 问题类型元数据 + 金额提及字段 → 可统计"预算执行率低"在 N 省出现、涉 X 亿 |
| 人天成本评估 | 问题的可技术化程度分类 | 问题定性元数据（数据缺失类/流程不规范类/制度类）→ agent 按类估算 |
| 技术可解决占比 | 同上，且需要根因归类 | 条目级元数据是 agent 根因分析的原料；**分块本身不产出占比** |
| 全国方向 × 各省厅长视角 | 省份/年度过滤 + 板块维度 | 省/年/板块三元元数据 → 按省切片、按板块聚合 |

**诚实边界**：后两项（根因、占比）是 agent 综合推理的产物，分块只能保证喂给模型的原料是"结构干净、可聚合、可溯源的条目全集"。估计分块+元数据对最终答案质量的贡献是**前提条件级**（原料不合格则全盘皆错），而非解决方案主体；综合层需要 agent 工作流配合（自定义 agent + hybrid-search + 元数据过滤），不在本文档范围。

## 5. 实施路径（三档，含排除理由）

| 路径 | 内容 | 收益 | 成本 | 取舍 |
|------|------|------|------|------|
| **A 配置层**（立即） | child_chunk_size 384→600 左右（对齐条目均长）；separators 保持；确认 auto 策略选中有 heading tier；auto_tag 指令中补充问题类型枚举 | 低~中：块稍微完整，但边界仍按段落 | 0 | **做**，但单独做解决不了 §1 的 #2/#3 |
| **B 预处理层**（优先） | 上传前清洗脚本：HTML→正文 markdown；mineru 输出去脚注残片；超短块策略；重复检测 | 高：直接消灭 §1 #2/#3/#4/#5 | 小：独立脚本，不动仓库代码 | **最优先**——解析噪声占比最大，且不依赖二开 |
| **C 二开层**（wkj-dev） | chunker 新增"审计文体感知" tier（§3.2 规则表），省份/年度/板块写入 chunk metadata 字段 | 最高：条目级完整 + 可聚合 | 大：`internal/infrastructure/chunker/` 定制 + 重新解析全库 | **方向确定后做**；先 B 验证原料质量，再决定 C 的投入 |

被排除的方案及理由：
- **调大 child_chunk_size 一刀切到 2000**：块不再碎，但一条块里混多个条目，向量相似度被稀释，聚合召回更差。排除。
- **关闭 parent-child 改单层大块**：丢失 parent 上下文供给（引用展示用 parent），且 WeKnora 引用协议按此设计。排除。
- **换 embedding/加 rerank**：不解决边界与元数据问题，属于另一个维度的优化。本方案之后再说。

## 6. 评测先行（对齐"数据我验"铁律）

用真实消费问题作 golden query，动分块前先建评测集：

1. **Golden 问题集**：以"财政软件公司老板找商机"场景出 5~10 个聚合问题（如"列出各省反映地方政府债务问题的条目及金额"），人工标注期望命中的条目。
2. **指标**（全部可机器度量）：
   - 条目完整率：以"一是/二是"为单位，条目不被切断的比例（当前基线待测）
   - 噪声块占比：导航/脚注/超短块占全库块数比例（当前基线：湖南类 HTML ≈ 100%，PDF 也有残片）
   - 聚合召回率：golden 问题召回的省份/条目覆盖度
3. **流程**：改前测基线 → 每档改动后重测 → 数字说话。`POST /chunker/preview` 端点可在不重建索引的情况下预览切分效果（`routes_knowledge.go` 的 `RegisterChunkerDebugRoutes`），用它做切分调试，避免反复全库重解析。
