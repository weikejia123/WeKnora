1先建立全局印象：数据存在三个地方

这是最容易被忽略、但最影响理解的一点：WeKnora 的数据不是存在一个库里。

为什么不都用 PostgreSQL？因为知识图谱要被反复「按关系跳转」——从实体 A 找它关联的实体 B，再找 B 关联的 C。这种多跳查询用 SQL 写会非常笨重，图数据库天生擅长。代价是它成了唯一需要额外运维的存储。
存储放什么为什么放这
PostgreSQL知识库、文档、分块、标签、Wiki、向量、队列状态有事务、有外键、扩展够用（pgvector 存向量，ParadeDB 做 BM25）
Neo4j实体、关系多跳关系查询是它的主场
文件存储原始文件大二进制不该进数据库
ⓘ 向量库可以换：除了默认的 PostgreSQL，向量索引还支持 Elasticsearch、Qdrant、Milvus、Weaviate、SQLite 六种引擎，按知识库粒度绑定（vector_stores 表）。换引擎不影响文档与分块模型——那是两件事。

2四层数据模型：从容器到最小检索单元

抛开存储不谈，逻辑上就四层，一层套一层：

第一层：知识库（KnowledgeBase）——决定「怎么加工」

它不只是个文件夹，真正的价值在配置。最关键的是四个索引开关：

开关开启后产生什么默认
vector_enabled向量索引，支持「意思相近」的语义检索开
keyword_enabledBM25 关键词索引，支持精确词命中开
wiki_enabled从文档自动生成 Wiki 页面关
graph_enabled抽取实体与关系，建知识图谱关
这是整份文档最重要的一张表。它解释了为什么同一个知识库，有人检索很准、有人什么都搜不到——四个开关决定了几条索引流水线跑不跑。默认只开向量和关键词，Wiki 和图谱是要主动开的。

除开关外，知识库还记录了：分块配置、图片处理配置、以及绑定的各类模型（向量 / 摘要 / VLM / ASR / Wiki 合成）。这些配置在创建文档时被读取一次，之后改知识库配置不会自动重跑已有文档。

第二层：文档（Knowledge）——「原料」

字段组含义
身份id / title / type / knowledge_base_id
来源source（URL 或 manual）、channel（从哪个入口进来）
状态parse_status、summary_status、pending_subtasks_count
文件file_name / file_type / file_hash / file_path / storage_size
目录folder_path——只影响展示与导航，不决定文件实际存哪
两类元数据metadata（系统写入的摄取状态）vs custom_metadata（用户自己写的）
ⓘ channel 记录了文档从哪来：网页上传、API、微信、浏览器扩展等。这解释了为什么浏览器里抓到的内容能直接进知识库——它在入库时被打上了对应的来源标记。

第三层：分块（Chunk）——下面第 5 章单独讲

它是检索的最小单元，字段最密，值得单独一节。

第四层：三种派生物

向量索引、图谱、Wiki 都是从分块派生出来的，有各自的存储和生命周期：

产物从哪来存在哪
向量 / 关键词分块的文本内容PostgreSQL 的 embeddings 表
实体与关系分块内容经模型抽取Neo4j
Wiki 页面多份文档跨文档合成PostgreSQL 的 wiki_pages

3文档的一生：5 个处理阶段

一份文档上传后，会经过五个有名字、有先后依赖的阶段。这不是我的归纳——代码里定义了一张明确的依赖表。

阶段做什么失败会怎样
1 文档解析把 PDF / Word / 图片等转成文本整条链断掉，文档标记为失败
2 分块把长文本切成一段段后续三个阶段全部变成「取消」
3 向量化把每块转成向量，写进索引该文档检索不到，但其他阶段可继续
4 多模态图片 OCR、图注生成仅影响图片内容，纯文本不受影响
5 后处理统一调度收尾：摘要、问题生成、图谱抽取、Wiki 生成等主体内容已可用，富化内容缺失
「取消」和「失败」是两个不同状态：某个阶段自己出错叫 failed；因为上游阶段失败而根本没轮到它跑，叫 cancelled。界面上这两种会分开显示——「你坏了导致我没跑」和「我自己坏了」是两回事。
ⓘ 第 5 阶段是「收尾总调度」：摘要生成、问题生成、图谱抽取、自动打标签、知识库画像等都挂在它下面。所以文档显示「已完成」但摘要还没出来，通常不是出错，而是这些富化子任务还在排队（此时状态是 finalizing）。

4解析状态机：用户看到的进度条

状态含义你在界面上会看到
pending已入库，还没开始处理排队中
processing主流程运行中解析进度条
finalizing正文已好，富化子任务在跑看起来像「快好了但还没好」
completed全部结束可用
failed出错失败原因
deleting正在删除（防止并发任务打架）删除中
ⓘ finalizing 配了一个计数器：pending_subtasks_count 记录还没完成的富化子任务数（摘要、问题、图谱分块）。它只在 finalizing 阶段有意义，进入终态后归零。

5分块（Chunk）：检索真正命中的东西

你搜问题时，系统命中的不是「文档」，而是具体的某一段——那就是分块。它的字段设计里藏着不少机制。

字段作用
content当前文本内容（可能被人工编辑过）
source_content解析器产出的原始文本，不可变。人工编辑时用来回滚与对照
content_revision每次编辑或回滚加一
index_status当前内容是否已同步进索引（ready / processing / failed）
chunk_index在原文档中的顺序位置
start_at / end_at在原文中的字符起止位置
pre_chunk_id / next_chunk_id前后相邻块的链接
chunk_type类型：正文 / 摘要 / 图片等
parent_chunk_id指向父块（图片块挂在正文块下）
relation_chunks图谱算出的直接关联块（缓存）
indirect_relation_chunks二度关联块（缓存）
context_header索引时拼在正文前的 Markdown 标题面包屑
is_enabled可临时关掉某块，让它不被检索
为什么要分 content 和 source_content？因为分块允许人工编辑。编辑会污染原始解析结果，所以保留一份不可变的原始版本——既能回滚，也能在编辑后按同样的输入重建索引（context_header 也是为此持久化的）。
ⓘ 图谱的结果缓存在分块表里：relation_chunks 和 indirect_relation_chunks 就是图谱算出的「这块跟哪些块有关系」的结果。为什么要缓存？因为图谱在 Neo4j，每次检索都去查图太慢——算一次存在这里，检索时直接读。

分块周围的表

表存什么
chunks分块本体
chunk_revisions分块的历史修订
embeddings向量与全文内容（向量检索与 BM25 共用）
knowledge_tags
knowledge_tag_relations		标签及其与文档的关联

6Wiki：文档的二次创作，以及那条证据链

Wiki 不是文档的另一种存法，而是跨文档综合出来的新内容。一份文档可能贡献到多个 Wiki 页面，一个页面也可能由多份文档合成。

它最值得理解的是回指设计——每个 Wiki 页面都能告诉你「我是从哪些文档、哪些分块变来的」。

Wiki 页面的字段要点

字段说明
slugURL 友好标识，形如 entity/acme-corp，在库内唯一
page_type页面类型：摘要 / 实体 / 概念 / 索引 / 综述 / 对比
status草稿 / 已发布 / 已归档
content / summaryMarkdown 正文与一行摘要
aliases别名、缩写、译名——用于搜索时匹配同一事物的不同叫法
source_refs来源文档（格式 文档ID|标题）
chunk_refs来源分块的具体 ID
in_links / out_links谁链到我 / 我链到谁（页面双链）
folder_id 等目录树位置。真正的位置只由 folder_id 决定，其余是缓存副本
version版本号。只有内容真的变了才加一，纯维护写入不动它
last_edit_source这一版谁写的：流水线 / 智能体 / 用户 / 回滚
ⓘ Wiki 有五张表：页面本身、页面修订历史、文件夹树、页面问题（issue）、操作日志。修订表每改一版存一份快照，可以回滚到任意历史版本。
别把「Wiki 的链接图」当成「知识图谱」。Wiki 也有 nodes/edges 结构，但它的节点是页面、边是页面间的超链接（in_links/out_links）。而知识图谱的节点是实体、边是语义关系，且存在完全不同的数据库里。两者名字都叫 graph，实质毫无关系。
对一下界面（这条最容易踩）：知识库页面上的「图谱」标签，显示的就是本节的 Wiki 链接图，不是知识图谱。三条判断依据：
① 该标签只在 Wiki 类型知识库上出现（前端显示条件是 isWiki，KnowledgeBase.vue:2224）；
② 它的数据来自 GET /api/v1/knowledgebase/{id}/wiki/graph，前端注释原文是 wiki link graph，返回类型 WikiGraphData；
③ 图例里的类型筛选（摘要 / 实体 / 概念 / 综述 / 对比）正是 Wiki 的页面类型。其中的「实体」指的是「这个 Wiki 页面讲的是某个实体」这一分类，不是知识图谱里的实体对象。
所以：看到「图谱」标签里有节点和关系，并不代表知识图谱开启了。

7知识图谱：唯一不在关系库里的数据

开启 graph_enabled 后，系统会让模型从分块里抽取实体和关系，存进 Neo4j。

对象字段
实体 EntityID、标题、类型、描述、出现的分块列表、出现频次、连接度
关系 Relationship起点、终点、描述、强度（1–10）、权重、出现的分块列表、两端连接度之和

图谱在检索里怎么用

它不直接给你答案，而是扩充上下文：

  • 直接关联块（GetRelationChunks）：跟命中块有直接关系的其他块，一并取来
  • 二度关联块（GetIndirectRelationChunks）：通过中间实体间接连上的块，用于再扩散一层

结果就缓存在前面提到的分块表 relation_chunks / indirect_relation_chunks 字段里。

图谱是可选增强，不是必需。它依赖外部图数据库、抽取要调模型（慢且花钱），所以默认关闭。不开图谱时，其他三种索引完全正常工作。
ⓘ 知识图谱在界面上没有独立可视化页面：整个前端里它只出现两处——知识库编辑器的「知识图谱抽取」开关，以及知识库列表上的「知识图谱」特性徽章。它会通过检索间接生效：把实体关系扩展成额外的候选分块（缓存到 relation_chunks），并在智能体侧提供图谱查询工具。想知道「图谱开了没有」，看开关和徽章即可，别去看那个图谱页面。

8检索机制：9 路召回怎么合成一个答案

提问时，系统并不是「搜一次、取前几条」，而是多路并行召回、再层层收敛。

代码里定义了 9 种具体的召回来源，每一路取回的证据都带「我是怎么被找到的」标记：

召回方式找什么
向量匹配意思相近的分块
关键词匹配精确词命中的分块（BM25）
相邻块匹配命中块的上下文前后段
父块匹配命中块的父块
关系块匹配图谱算出的直接关联块
图谱匹配沿实体关系跳转到的新分块
历史匹配本会话历史里出现过的内容
网络搜索外部网页（需先配搜索服务）
数据分析从表格类数据里算出结果
「为什么换个问法就搜到了」有了答案：四路召回各有各的盲区。向量适合意思相近但用词不同，关键词适合精确术语；某一问法下某一路召回为空，换个说法可能就命中了。这不是系统不稳定，是设计使然。
ⓘ 查询理解与改写：问题进来后会先被理解和扩展（query_understand / query_expansion），再分发给各路召回。所以「同一个问题，模型看到的查询词可能不止一个」。

9异步任务：11 个队列怎么排队

前面所有处理都是异步的——上传接口立即返回，实际工作在后台队列里做。队列不是随便设的，它按工作池分组，不同池走不同并发资源。

队列工作池跑什么任务
defaultcore文档处理、手工知识更新
chat_attachmentcore对话里临时上传的附件解析
post_processpost_process知识后处理总调度
summaryenrichment摘要、表格摘要、自动打标、知识库画像
multimodalenrichment图片 OCR 与图注
graphenrichment图谱抽取
questionenrichment问题生成
memoryenrichment记忆抽取
syncmaintenance数据源同步
maintenancemaintenanceFAQ 导入、克隆、删除、批量重解析、移动
wikiwikiWiki 同步与收尾

每个队列带权重，决定它在所属工作池里分到多少处理能力。比如 chat_attachment 权重高于 default——这样一次大批量知识库导入不会把聊天里上传的附件堵在后面。

任务失败不会丢：有 task_dead_letters（死信表）记录最终失败的任务，task_pending_ops 记录待执行的补充操作。排查「某个文档一直没处理完」时，这两个表是线索所在。
ⓘ 处理过程可观测：每个文档的处理都会写一棵 span 树到 knowledge_processing_spans——哪个阶段、耗时多少、输入输出是什么、错在哪。这就是「处理详情」时间线的数据来源。

五个常见困惑

Q1：文档显示「已完成」，但摘要/图谱没有？

看 finalizing 与 pending_subtasks_count。富化任务是第 5 阶段下的子任务，排队慢于主流程是正常的。真正卡住时查 task_dead_letters。

Q2：为什么开了 Wiki 但没生成页面？

Wiki 是知识库级开关，且生成是有上限的（max_pages_per_ingest），并且要在文档处理流程里被触发。配置改了不会自动重跑历史文档，需要重新处理。

Q3：改了分块内容，检索结果会变吗？

会，但不是立即。编辑后 index_status 会变成处理中，需要重新索引。source_content 始终保留原始解析结果，可随时回滚。

Q4：没开知识图谱，为什么「图谱」页面有节点和关系？

因为那个页面画的是 Wiki 链接图，不是知识图谱——节点是你的 Wiki 页面，边是页面正文里的 [[双链]]。三条判断依据见第 6 章末尾的提示。真正的知识图谱在界面上只有开关和徽章，没有可视化页；两者同名不同物，一个在 PostgreSQL、一个在 Neo4j。

Q5：为什么同一份文档，别人搜得到我搜不到？

先确认三件事：知识库是否共享给你、分块是否被禁用（is_enabled）、检索走的是哪几路召回（四个索引开关）。多数「搜不到」出在权限或索引开关上。
