## 零、两个问题的答案，先摆在这里

| 问题 | 结论 |
|---|---|
| 文本文件「存成二进制」后向量化，还能和文字呼应吗？ | **能，前提是解码正确。** 解码正确时，你的向量与「复制内容出来再向量化」**逐位相同**（同一个模型、同一段字符串 ⇒ 同一个向量）。解码错误时，得到的是乱码的向量，与原文毫无关系。 |
| 整文件向量化 vs 内容向量化，有区别吗？ | **对文本文件：技术上不存在「整文件向量化」这个操作**，中间必过 tokenizer，而 tokenizer 只吃字符串，所以一定要先解码。真正有区别的是「解码得对不对」，不是「从哪读」。 |
| 那图片呢？ | **要分两个问题。** 「换存储格式」和文本换编码完全对等（PNG↔JPEG 解码后像素几乎一致）；但「像素里有没有字母 A」这件事，文本和图片有本质差别 —— 见第一节。 |
| 文本 ABC 和图片 ABC，向量接近吗？ | **在字节层和原始数值层完全不接近，必须靠模型训练才会被拉到一起。** 这是本文最容易被误解的一处，见 1.4。 |

一句话：**「二进制」不是一层，是两层被混在一起叫了** —— 文件容器层（字节）和内容层（字符/像素）。向量化只发生在内容层。

## 一、把「二进制」这个词拆开

日常说「文件存到磁盘都是二进制」，把三件不同的事压成了一个词：

| 层 | 是什么 | 文本文件的例子 | 图片文件的例子 |
|---|---|---|---|
| **L1 字节层** | 磁盘上的 0/1，文件的物理表示 | `知识` → `E7 9F A5 E8 AF 86`（UTF-8） | JPEG 的 DCT 系数、霍夫曼编码流 |
| **L2 内容层** | 解码后真正的载体 | 字符序列 `知识` | 像素矩阵（RGB 数值） |
| **L3 语义层** | 模型产出的向量 | 一个 1024 维 float 数组 | 一个 1024 维 float 数组 |

**关键差别在这一步**：

- 对**文本**，L1 → L2 是「**查表**」。`E7 9F A5` 就是「知」的另一种写法，不是「知」的另一种东西。换编码（UTF-8 ↔ UTF-16 ↔ GBK）只改字节，不改字符。**这张表是 ISO/RFC 定死的，不需要模型。**
- 对**图片**，L1 → L2 是「**解压 + 反变换**」。`50 4B 03 04`（PNG）不是像素的另一种写法，是像素压过之后剩下的东西。解码之后你得到**像素**，而像素里**没有「文字」这个东西**。

所以：

```
文本文件：  磁盘字节 ──查表(标准,无需模型)──► 字符 ──tokenizer──► 向量
图片文件：  磁盘字节 ──解压反变换──────────► 像素 ──视觉编码器──► 向量
                                              ↑ 这里只有坐标和灰度，
                                                没有"字母"这个东西
```

向量化永远发生在箭头右边。**「对二进制向量化」在技术上不成立** —— 没有哪个 embedding 模型吃字节。

### 1.1 先纠正我上一轮说错的地方

我上一轮强调「JPEG 字节是有损残差」，这句话**本身没错，但用错了地方**。你的反驳是对的：

> 把它显示出来，不就是有损压缩后残差的正常显示吗？

**对。** 而且这正好说明「格式」和「内容」是两件事：

| 同一张 ABC 图，换存储格式（本机实测） | 字节数 | 前 8 字节 |
|---|---:|---|
| PNG | 2,069 | `89 50 4E 47 0D 0A 1A 0A` |
| JPEG | 2,366 | `FF D8 FF E0 00 10 4A 46` |
| BMP | 21,654 | `42 4D 96 54 00 00 00 00` |

三者字节流**完全不同**，长度差 10 倍。但解码成像素后：

> PNG 解码 vs JPEG 解码，21,600 个分量里差异 > 8 的只有 **483 个（2.24%）**。

⇒ **「换存储格式」这件事，图片和文本是对等的**：文本是 UTF-8↔GBK 换编码，图片是 PNG↔JPEG 换格式，都是「只改字节，不改内容」。你这句话的直觉完全正确。

**真正的差别在下一步**，也就是你举的 A、B、C 那个例子。

### 1.2 文本里的「ABC」：磁盘上真的有 A、B、C

```
abc.txt 内容为 ABC
  磁盘字节: 41 42 43
  逐字节看: 41='A'   42='B'   43='C'
```

**0x41 就是 'A' 本身。** 这是 1970 年代定死的标准查表，不需要任何模型。而且：

- 换字体（Helvetica→Times）：字节 `41 42 43` **一位不变**
- 换字号、换编辑器、换操作系统：字节不变

⇒ 文字的字形（长得像什么）和它的编码（0x41）是**完全解耦**的两件事。所以「你写 ABC，磁盘里就真有 A、B、C」这句话，在文本上是成立的。

### 1.3 图片里的「ABC」：像素里没有任何一个数值是 A

同一张写着 ABC 的图（120×60，7,200 个像素，其中 1,020 个是黑色笔画）：

```
前 8 个黑色像素：
   ( 82,  6) 灰度= 75
   ( 83,  6) 灰度= 37
   ( 84,  6) 灰度= 13
   ...
```

**注意：这里没有任何一个数值是 'A'。** 只有一堆坐标和灰度值。

- 「A」这个形状，是这些坐标**连起来之后**，靠**你的眼睛**才认出来的。
- 像素里没有「字母」这个东西。**A 是观察者的产物，不是数据的属性。**

最直接的证据：把同一段 ABC 换成 Times 字体，黑色像素从 1,020 个变成 1,204 个，**坐标全变了** —— 但人看还是 ABC。文本那边换字体，字节一位都不变。

⇒ **这是文本和图片的根本分界：**
> **文本：内容已经以符号形式存在，字节就是符号。**
> **图片：内容只以几何形式存在，「符号」要靠识别才产生。**

### 1.4 那么，图片是怎么被「向量化成接近 ABC」的？

这正是你的问题：**为什么一堆坐标，向量化之后就跟 ABC 接近了？**

答案是：**不是因为像素里藏着 ABC，而是因为编码器被训练成忽略无关变化、保留形状。**

用本机实测一个小实验说明（把 120×60 像素压成 8×8 的布局特征，丢掉全部细节）：

| 比较对象 | 像素坐标相同吗 | 编码后余弦 |
|---|---|---:|
| ABC·Helvetica vs ABC·Times | **否（完全不同）** | **0.960** |
| ABC·Helvetica vs ABC·Arial | **否（完全不同）** | **0.865** |
| ABC·Times vs XYZ·Times | 否 | 0.877 |
| ABC·Helvetica vs XYZ·Arial | 否 | 0.799 |

（真实模型复杂千万倍，但对「换字体」的鲁棒性，原理完全一样。）

**像素坐标一个都对不上，但同字母异字体的余弦接近 1。** 这说明编码器在做一件文本那边**不需要做**的事：

> **把「字体、字号、位置、抗锯齿、压缩噪声」这些与语义无关的变化丢掉，只保留形状特征。**

这个「知道什么该丢」的能力**不是从字节里读出来的，是训练出来的** —— 它来自模型见过几亿张图和文字对的配对。文本那边没有这一步：UTF-8 的查表是标准，不需要「学会忽略字体」。

### 1.5 直接回答：文本 ABC 和图片 ABC，向量接近吗？

**在字节层和原始数值层，完全不接近。** 本机实测：

| 比较 | 余弦 |
|---|---:|
| `abc.txt` 的字节 vs `abc.png` 的字节 | **0.084** |
| 「'ABC' 的三个字符值」vs「7,200 个像素灰度」 | **0.000** |

原因很直白：两边根本不在同一个坐标系里。

```
文本那侧：只有 3 个数    {65:1, 66:1, 67:1}
图片那侧：7,200 个数，204 种灰度
```

**没有任何自动的对应关系。** 它们能被映射到同一个向量空间，**100% 是模型训练的结果**，不是数据的性质。

这就引出一条很重要的判别：

> **多模态模型说「文字 ABC」和「图片 ABC」相似，是模型的判断，不是可验证的事实。**
> 而「文本 ABC」和「文本 ABC 的副本」逐位相同，这是数学，可验证。
>
> 前者可能出错（幻觉、字体太怪、图太糊），后者不可能出错。

⇒ 这就是为什么图片归档要保守（见第三节），文本归档可以大胆。

## 二、第一问：文本文件，整文件 vs 内容，到底一样不一样

### 2.1 「整文件向量化」实际发生了什么

WeKnora 的入库链路（`internal/infrastructure/docparser/builtin_converter.go` 的 `SimpleFormatReader.Read`）：

```
原始字节 ─► decodeText() ─► 字符串 ─► 分块(chunker) ─► 每块文本 ─► embedding 模型
```

`decodeText` 明确按这个顺序尝试：UTF-16 BOM → UTF-8 校验 → GB18030 → Windows-1252 → Latin-1。
（这段代码的注释自己写明了：取错编码的 GBK 文件「到达索引时是一段非法字节」。）

**所以你问的两种做法，在 WeKnora 里是同一段代码**：都是从磁盘读字节 → 解码 → 切块 → 向量化。区别只在于解码这一步对UTF-8文件是恒等变换，对GBK文件是真正的转码。

> 如果你自己写脚本「把整个文件 read() 出来直接喂模型」，那 Feed 进去的其实是 Python 的 `bytes`，HTTP 客户端会再按某种编码把它变成字符串（通常是 UTF-8，失败则报错或替换）。这一步等价于「强制按 UTF-8 解码」，后果见下节。

### 2.2 解码正确 ⇒ 逐位相同

同一段文字、同一个模型、同一组参数：

- `open(f,'rb').read().decode('utf-8')` 得到字符串 S
- 手动全选复制粘贴得到字符串 S
- 二者 **S 相同**，tokenizer 输出相同，向量 **逐位相同**

差别只在「有没有多带一个 `\n`」「有没有带上标题行」。WeKnora 会主动往索引内容里拼文档标题（`internal/application/service/knowledge_index_content.go` 的 `buildKnowledgeIndexContent`），这是有意的，不是编码问题。

⇒ **这一问没有悬念：解码正确时，两者没有区别。**

### 2.3 解码错误 ⇒ 向量变成噪声（这才是真风险）

拿本机一个真实文件实测（`~/CODE/WORK/.../预算执行信息系统4.0参数更新操作说明.docx`，483,634 字节）：

| 检查项 | 实测结果 |
|---|---|
| 前 4 字节 | `50 4B 03 04` ⇒ 是 **ZIP 容器**，不是文本 |
| 原始字节里能直接看到的中文字符数 | **0 个** |
| 能整体按 UTF-8 解码吗 | **否**，第 15 字节就失败 |
| 强制按 UTF-8（替换错误）解码 | 458,911 字符，其中 **44.1% 是 U+FFFD 替换符** |
| 解出 `word/document.xml` 后剥标签 | 88 个字符，是一条完整可读的说明 |

⇒ 对 docx 的**原始字节**做 embedding，得到的是**对一段 ZIP 压缩流的 embedding**。虽然 tokenizer 不报错（它看到的是 `PK\x03\x04…` 和一堆替换符），但这段输入与「这份文档说了什么」在语义上**没有任何对应关系**。检索时它既不会被召回，也不会污染别的块 —— 它只是一个占位的噪声向量，白花钱。

再看编码敏感性（本机实测，同一段中文）：

| 两个版本 | 字节直方图余弦相似度 |
|---|---|
| UTF-8 vs UTF-8（自身） | 1.000 |
| UTF-8 vs UTF-8 + CRLF 换行 | 0.997 |
| UTF-8 vs UTF-16LE | **0.160** |
| UTF-8 vs GB18030 | **0.236** |

这是**字节层的**差距。同一段文字换编码，字节层几乎变成另一样东西 —— 而语义模型对它俩都会给出 1.000（因为解码后是同一个字符串）。**这张表恰好说明：差距 100% 发生在解码那一步，解码之后就没了。**

### 2.4 小结论

> 文本文件的向量化质量，**不取决于「它是二进制」，取决于「解码是否命中正确编码」**。
> 编码判错 = 向量报废；编码判对 = 与复制粘贴完全等价。

好消息：WeKnora 的 `decodeText` 已经覆盖了 UTF-8/GB18030/Windows-1252/Latin-1/UTF-16，本机 600 份 txt/md/csv 抽样里 99.5% 是 UTF-8（其中 36% 含中文），另有 3 份「.txt 其实是 DDS 图片」的假扩展名 —— 这是另一类问题（见 4.4）。

## 三、第二问：图片为什么是另一回事

### 3.1 图片没有「原文」可解

`照片.jpg` 的字节里没有一段文字等你解码。它有的是压缩后的 DCT 系数。所以「把内容复制出来向量化」这个操作，对图片**不存在对应物**。

但这不是重点。重点是 **1.3 那条分界的后果**：图片的内容只以几何形式存在，「里面写了什么」是**识别出来的**，不是**解出来的**。所以图片入库没有「正确值」可以对齐 —— 只有一个**模型的判断**，而判断会错。

下表的「可靠性」一列，说的正是这件事：

| 路径 | 做法 | 向量代表什么 | 可靠性 |
|---|---|---|---|
| **A. VLM 转述** | 多模态大模型看图，写一句 caption / 做 OCR | 「这张图被描述成的那句话」 | 中 — 依赖模型，会漏细节、会幻觉 |
| **B. 多模态编码器** | 图像编码器直接吃像素，出向量 | 像素的形状特征（见 1.4） | 中高 — 对「以图搜图」强，对「问细节」弱 |
| **C. 只存不算** | 登记元数据，不向量化 | —— | 高（不产生假信息） |

注意 A 的行为有个容易忽略的后果：**caption 一旦生成，就变成了「文本」**。之后它走的是和 txt 文件完全相同的文本向量化路径。所以「图片入库」实际上常常退化成「一段由模型写的文字入库」—— 图片本身的信息只以 caption 的忠实度为上限。**caption 漏掉的，向量里就没有。**

**WeKnora 当前走的是 A 为主、B 可选**（`internal/application/service/image_multimodal.go`）：

- 先由 VLM 生成 caption（可选同时 OCR），产出 `ChunkTypeImageCaption` / `ChunkTypeImageOCR` 两种文本块 → 这些块照常做**文本向量化**。
- `indexImageVector` 再尝试额外产出一个**图像向量**块，但注意它的 `Content` 字段仍然写的是 caption/OCR 文本 —— 也就是说，**即使走了图像向量，块的可读内容依然是文字**。图像向量只参与相似度计算，回答时用不上。
- 而且它有明确的质量判断，代码注释写着：「一页被扫描的文档本质是文本，OCR 块比图像向量表达得更好：多模态 embedding 在最密集的文本上恰恰最弱」。所以扫描页会被跳过图像向量。
- 前提是 `embedding.AsImageEmbedder(model)` 成功 —— 也就是**当前配置的 embedding 模型必须支持图像输入**。你现在用的是 `bge-m3`（纯文本），所以**图像向量这条路目前是关的**，只剩 caption 文本。

### 3.2 多模态「统一空间」不等于可以随便混比

这一点必须写清楚，因为它直接影响你选 Google 新模型的动机：

- `gemini-embedding-2` 确实把文本、图像、视频、音频、PDF 映到**同一个**向量空间，理论上「用文字检索图片」可行。
- 但**不同代模型的空间不兼容**：`gemini-embedding-001` 与 `gemini-embedding-2` 的向量**不能互相比较**，升级必须全量重算。（官方文档明写）
- 「统一空间」解决的是跨模态检索，**不解决长文档检索**。

## 四、Gemini Embedding 2 到底行不行 —— 先纠正我自己的错

> **上一版这一节写错了，这里重写。**
> 我把「直接送整份 PDF」这个**可选功能**，当成了**模型的能力上限**，据此得出「6 页截断所以不能做主力」。这个推理是错的 —— 因为 **WeKnora 从来不拿整份文件去算向量。**

### 4.1 那个 8192 token 上限，在你的链路里根本碰不到

WeKnora 的向量化单位是 **chunk**，不是文件：

```
文件 ─► 解析出文本 ─► 切成 chunk（默认 512 字符）─► 每 chunk 单独算向量
```

所以：

| 项 | 数值 |
|---|---:|
| 默认 ChunkSize | 512 字符 |
| 中文每块约 | 约 410 token |
| Gemini 上限 | 8,192 token |
| **单块占上限** | **5.0%** |

⇒ **「超出静默截断」这件事，在 chunk 级永远触发不了。** 我上一轮拿整份 PDF 的页数去论证，是把可选的「文档级向量」当成必经之路了。**这是错的。**

同样，「每请求最多 6 张图」「每次 1 个 PDF」也是**单次调用的批量上限**，不是总容量 —— WeKnora 本来就是按 chunk 逐批发的。

### 4.2 那它真正的优势是什么（你说的这点是对的）

`gemini-embedding-2` 是**同一模型、同一向量空间**同时吃文本和图像。这意味着：

- **不需要两套模型**：不用「bge-m3 算文本 + 另配一个视觉模型算图」。
- **不需要 caption 中转**：图像直接进编码器，不经过 VLM 转述，**避开了 1.5 节说的「caption 漏掉就没有」那个信息损失**。
- 对「用文字找图」这类查询，直接在同一个空间里算距离，比「先转述再匹配」更直接。

这三点是实打实的优势，**而且正好补上了当前 gshare 归档方案里最弱的一环**（图片只能靠 caption）。

### 4.3 但有三条限制仍然成立

这三条不是我编的，是从代码和文档里核出来的：

**① 图像只吃 PNG 和 JPEG。** 手机实测：`internal/models/embedding/image_wire_test.go:277` 断言 `MIMETypes == ["image/png","image/jpeg"]`。对照你的 60,886 张图：

| 能直接送 | 43,001 张（png 33,426 + jpg 9,345 + jpeg 230） |
| 不能直接送 | **17,885 张**（svg 12,281 + webp 4,342 + gif 764 + ico 306 + bmp 82 + 其他） |

SVG 那 12,281 张本来该走文本通道，问题不大。但 **webp 4,342 张得先转码**。

**② 联网问题。** 你这台机器现在**直连不通**：实测 `generativelanguage.googleapis.com` 和 `ai.google.dev` 都是超时，而百度 0.1 秒、dashscope 0.24 秒都正常。生产环境走 Google API 需要稳定代理 —— **这是运维问题，但会变成可用性问题**。

**③ 换模型仍然要全量重算。** 这条与 8192 无关，是向量空间的性质：

- `gemini-embedding-001` 与 `gemini-embedding-2` **空间不兼容**，官方明写「must re-embed all your data」。
- WeKnora 侧还有一条硬限制：`rejectEmbeddingModelChange`（`internal/application/service/knowledgebase.go`）在**知识库已有文件时直接拒绝**改 embedding 模型，报错「知识库中已有文件，无法修改Embedding模型」。
- 更关键的是 `validateSameEmbeddingModel`（`knowledgebase_search_storegroup.go`）：**跨库检索要求所有 KB 用同一个 embedding 模型**，否则直接 400。

⇒ 这三条合起来意味着：**不同 embedding 模型的库，不能放在一次检索里。**

### 4.4 所以真正的约束不是「Gemini 行不行」，是「只能选一个」

这是整件事的关键，也是我上一轮没说清的地方：

> **WeKnora 的检索架构假设「一个租户的检索面只有一个向量空间」。**

| 能力 | 需要 | 能否与 bge-m3 共存 |
|---|---|---|
| 中文长文档检索 | bge-m3（1024 维，8192 上下文，中文强） | —— |
| 图像/跨模态检索 | gemini-embedding-2（3072 维） | **不能同一检索** |

**你不可能「文本用 bge-m3、图片用 Gemini」然后一次查询同时召回两者。** 会直接被 `validateSameEmbeddingModel` 拦下。

可行的只有两种摆法：

| 摆法 | 做法 | 代价 |
|---|---|---|
| **A. 全局换** | 所有 KB 都换成 Gemini Embedding 2 | 全库重算 + 重建所有 KB + 重调阈值；且失去 121 本机部署的自主性 |
| **B. 双库并行** | 文本库保持 bge-m3；图片单独建一个 Gemini 库 | 两次查询、结果在应用层合并；不能跨库 RRF |

**B 才是「个人/应用级」的合理选择**，因为它不动现有文本库，只加一路。代价是你要自己写合并逻辑。

### 4.5 还有一个更省事的选项：国产多模态 embedding

WeKnora 的模型目录里已经内置了几个**国内可达**的多模态 embedding（`internal/models/catalog/data/models.generated.json`）：

| 模型 | 维度 | 输入 | 供应商 |
|---|---:|---|---|
| `tongyi-embedding-vision-plus` | 1152 | text / image / video | 阿里（dashscope） |
| `tongyi-embedding-vision-flash` | 768 | text / image / video | 阿里 |
| `qwen3-vl-embedding` | 2560 | text / image / video | 阿里 |
| `doubao-embedding-vision-251215` | 2048 | text / image / video | 火山 |
| `jina-embeddings-v5-omni-small` | 1024 | text / image | Jina |

**注意 `tongyi-embedding-vision-flash` 是 768 维，`jina-...-omni-small` 是 1024 维** —— 1024 维和 bge-m3 **维度相同**，虽然不代表向量空间兼容，但至少省掉「维度不适配索引」这一层麻烦。而且这些走国内网络，没有代理风险。

⇒ **如果你的目标是「补上图片这一路」，先用国产多模态模型试，比用 Gemini 更省事。** 如果你的目标是「整体质量提升 + 全模态统一」，Gemini 确实更强，但代价是全局换。

### 4.6 关于成本，重算一遍

粗算（**假设**：文本类去重后 17.2GB，裸文本 md/txt/log/csv/ipynb 约 8.9GB，容器类 pdf/docx/xlsx/pptx 约 8.3GB 按体积 25% 折算有效文本，中文 2.6 字节/字符、0.8 token/字符）：

```
有效文本 ≈ 11 GB → 约 42 亿字符 → 约 3.4 B token
gemini-embedding-2 @ $0.20/M  →  约 $680（一次性）
```

**这个数字要放在正确的位置看**：$680 对生产不算什么，对个人是笔钱；但真正的成本不是这 $680，是**「锁死」** —— 一旦全库都是 Gemini 向量，以后想换回本地模型，成本是同样的 $680 再来一次 + 全部重建。

### 4.7 我的修正结论

| 你的目标 | 建议 |
|---|---|
| **文本检索质量**（当前主力） | **保持 bge-m3**。你说「够用」，`05-系统配置体检.md` 的选型分析也支持。没必要动 |
| **补上图片这一路** | **先试国产多模态**（tongyi-vision / qwen3-vl）。网络无障碍、维度可选 1024 |
| **要全模态统一 + 质量上限** | 用 Gemini，但接受「全局换」或「双库并行」，并解决代理问题 |
| **只是个人用、能解决问题就行** | **双库并行（方案 B）最合适** —— 文本库不动，图片单开一路，风险最低 |

> **核心判断：你的「应用级够用」这个定位，恰恰说明不该做全局换型。** 全局换型是给「要统一、要上限、能承担重建」的生产级场景准备的。应用级的正确做法是**加一路，不动主干**。

  - 抽样里出现了**小说章节**、**波斯语的 ComfyUI 文档**、**网页剪藏**。多语言、多体裁、无主题。

**这就是「二次派生物」的典型形态**：内容是别人写的，你只是抓过一份；它和原站点的关系比和你知识库的关系更近。而且它占了 14GB / 全盘 102GB 的 14%。

### 5.4 一个真问题：扩展名会撒谎

600 份 txt/md/csv 抽样里，有 3 份 `.txt` 实际是 **DDS 纹理图**（游戏/3D 资源），字节以 `DDS |` 开头，肉眼未审核就按文本入库会得到 100% 的噪声向量。

⇒ 入库前必须做**内容嗅探**（magic bytes / `file(1)`），不能只信扩展名。这一条同样适用于「.md 里其实是 HTML」「.doc 是 RTF」等情况。

### 5.5 一个好消息：向量索引的坑已经被上游填了

`13-检索性能与索引/WeKnora-向量索引维度覆盖缺口.md` 当时记录：2560 维没有 HNSW 索引，向量检索走全表扫描。

**该问题上游已修**：`internal/application/repository/retriever/postgres/hnsw_index.go`（PR #3364，2026-11-02，已在当前 HEAD）。现在应用会在首次遇到新维度时，**后台自动** `CREATE INDEX CONCURRENTLY` 建部分索引。

⇒ 但**新维度第一次写入时后台建索引**意味着：百万级文件批量入库后，头几次查询会慢，且索引构建期间有 IO 压力。**批量导入要排队执行，别和实时问答抢**。

## 六、技术选型上的三条判断

### 6.1 「单向量 per 文件」是错的，必须切块

3,036 个 PDF 平均 1.8MB（约 90 万字/份），压成一条 3072 维向量意味着：这份文档的每一个细节都被平均到同一个方向。查询「某条具体规定」时，向量与查询的相似度被稀释到几乎与随机相同。

WeKnora 现有默认（`internal/infrastructure/chunker/splitter.go`）：`ChunkSize=512` 字符、`ChunkOverlap=80`；parent-child 模式下 parent 4096 / child 384。

`06-知识体系设计/WeKnora-审计报告知识库分块方案（讨论稿）.md` 已经就「等长子块对聚合型查询是错配」给出过完整论证，**结论可直接复用**：分块的原子单元应该是**业务条目**，不是字数。

### 6.2 「元数据」比「向量」更决定成败

110 万文件里 18.3 万个连文件名都没有。这样的东西即使向量算得再准，也没法回答「这是哪来的、什么时候的、属于哪个项目」。

`06-…分块方案` 已经点明：**元数据决定聚合检索的可能性**。这条在归档场景下更严重 —— 因为你面对的不是 100 份文档，是 100 万个。

⇒ **归档的第一步不是向量化，是「建立身份」**：路径、扩展名、大小、MD5、创建/修改时间、来源目录、所属项目、内容类型。这些在扫描 CSV 里**已经有了**，直接可用。

### 6.3 SVG / 小图标 / 代码，各有各的通道

| 类型 | 正确处理 | 错误做法 |
|---|---|---|
| `.svg` | 当 XML 文本解析（它本来就带 `<title>`/`<desc>`/文字节点） | 当位图送视觉模型 |
| 图标、<10KB 图 | 跳过，或只登记不向量化 | 全部做 caption（20,765 次模型调用买回 0 信息） |
| 代码文本 | 按语言/符号切分（函数、类），保留文件路径做上下文 | 按 512 字符硬切（切断函数体） |
| 压缩包 | **先列清单，不展开**，按需解 | 全量解包再入库 |
| 音视频 | ASR → 文本 → 文本向量 | 直接对多媒体做向量（当前没有这类模型） |

## 七、归档方案建议：四层，且必须是「漏斗」不是「全量」

核心判据只有一条：**这个东西能不能被重新生成？**
能重建的（node_modules、dist、agent 缓存、抓取副本）→ **不进库**。这一条就能砍掉 90%。

```
                     110 万文件（去重后）
                            │
        ┌───────────────────┼────────────────────┐
        ▼                   ▼                    ▼
   L0 不归档            L1 只登记            L2 全文入库         L3 精编
  (可重建/无价值)      (有内容无身份)        (人的真实资产)     (结构化提炼)
   ~95 万               18.4 万                ~4 万              几百
```

### L0 不归档 —— 约 95 万文件

**判据**：能被原工具重新生成，或没有独立价值。

- `node_modules/`、`dist/`、`build/`、`.next/`、`target/`、`__pycache__/`、虚拟环境
- 各 Agent/工具链的缓存、日志（`Caches`、`OrbStack`、`~/.bun`、`~/.nvm` 等，扫描时已排除大部分）
- `.git` 内部对象（扫描时已排除）
- **本仓库自己的源码**（已在 git 里，走代码检索即可，不需进知识库）

**动作**：什么都不做。**这一步是最大的一步，也是最容易被忽略的一步。**

### L1 只登记，不入向量 —— 约 18.4 万（`.gshare/raw/0-md5-save` 为主）

**判据**：内容可能是别人的，但**没有身份**（无文件名、无来源、无时间），且是二次派生物。

**做法**：
1. 用扫描 CSV 的 MD5 建一张**清单表**（已有数据）。
2. **不调 embedding**。先用便宜的检索（BM25 / ripgrep / 文件名）覆盖。
3. 需要时**按需升级**：某个文件被真的查到了，再单独把它拉到 L2。

**为什么这样最划算**：这 18.4 万文件是 14GB、约 3.4B token，全量向量化要 $680 一次、重来得再来一次，而预期的召回量接近于零（无身份文件难以被查询命中）。**先花 0 元，等它证明自己有用来再说。**

### L2 全文入库 —— 约 4 万

**判据**：人真正产生或真正使用过的文档/图片。

| 来源 | 规模 | 处理 |
|---|---|---|
| `~/Downloads`、`~/Documents`、`~/Desktop` | 约 1,300 文档 | **全部入库**，这是真正的人类资产 |
| `~/Pictures` + 大图 | 约 5,200 图 | 筛选后入库（见下） |
| `~/CODE/WORK` | 277 文档 + 183 图 | **全部入库**（业务材料） |
| `~/CODE/my-agent-group/projects/*` 里的 `.md` | 数万 | **只收「结论型」文档**（分析报告、方案、复盘），不收过程日志 |
| 压缩包 | 3,729 | **只登记清单**，按需解 |

**图片的筛选规则**（把 60,886 降到约 24,500，再人工抽检）：
1. 排除 SVG（12,281，改走文本通道）
2. 排除 < 100KB（36,403，多为图标/UI 碎片）
3. 排除已 MD5 完全相同的副本（扫描已去重）
4. 剩下的按目录聚类，`Pictures` 优先，`CODE` 下的截图按项目归并

### L3 精编 —— 几百份

**判据**：要反复被检索、被引用、被聚合分析的核心知识。

这是一层**人工 + Agent 协作产出**的结构化条目，不是原文搬运。对应 `.gshare` 已经存在的那套设计：

- `schema/taxonomy.md` 定了 11 种页面类型：concept / domain / entity / project / agent / pattern / prompt / skill / rule / operation / decision
- `schema/frontmatter.md` 要求每页带 `type / title / status / tags / sources / related / updated`

⇒ **`.gshare` 的 wiki 层就是现成的 L3 规范，不用另起一套。** WeKnora 应该与它**对接而不是重复**：wiki 页是「编译后的知识」，WeKnora 是「原文的可检索底座」。

| 步 | 做什么 | 成本 | 产出 |

**不要跳步。** 第 3 步的基线召回率，是后面所有「要不要换模型 / 调什么参数」的唯一裁判。

## 十、一句话收尾

文本和图片的分界，**不在「都是二进制」这一层，而在「内容以什么形式存在」这一层**：

| | 内容存在于 | 向量化前要做的事 | 可否验证 |
|---|---|---|---|
| **文本** | **符号**（0x41 就是 A，标准查表） | 解码（查表，无需模型） | **可**：与副本逐位相同 |
| **图片** | **几何**（只有坐标和灰度，没有「A」） | 由模型**识别**出形状特征（训练得来） | **不可**：只有模型的判断 |

这解释了你那两个例子：
- 文本 ABC 和图片 ABC **在字节层毫无关系**（实测余弦 0.084），能被拉到一起**全靠模型训练**，不是数据自带的性质。
- 图片之所以「向量化后接近 ABC」，是因为编码器**学会了丢掉字体/字号/位置**这些无关变化 —— 这个能力文本那边不需要有。

⇒ 所以「一致不一致」这个问法，对两类文件要换成两个问法：
- **文本**：解码对不对？（可验证，对就一致）
- **图片**：转述/编码器可不可信？（不可验证，只能抽样评估）

你担心的「二进制导致向量对不上文字」，**只对一类文件成立**：那些**看起来是文本、实际是别的格式**的文件（docx 被当 txt 读、DDS 被当 txt 读、GBK 被当 UTF-8 读）。这类文件的向量确实是噪声。

对**正常文本**，二进制只是它的运输方式，解码之后完全一致。对**图片**，「一致」这个问题本身不成立 —— 它没有原文可对，只有转述的质量高低。

⇒ 真正要投入的不是「换个更强的向量模型」，而是 **① 先把文件认对（格式/编码/身份），② 再把该进的分层选对（95% 的文件不该进）**。这两件事做对，用现在的 bge-m3 就能拿到好结果；这两件事不做，换什么模型都是把噪声算得更快。
