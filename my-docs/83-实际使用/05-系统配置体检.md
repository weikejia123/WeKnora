| 模型 | 类型 | 实测 | 判定 |
|---|---|---|---|
| `qwen3.8-27b-ud-q4xl-gpu2` | KnowledgeQA | HTTP 200 | ✅ 可用（当前唯一能用的对话模型） |
| `qwen3.8-27b-ud-q4xl-gpu3` | KnowledgeQA | HTTP 400 | ❌ **已失效**——网关该条目 2026-10-25 已删除（GPU3 改驻 DeepSeek） |
| `minicpm-v-4.7-35b-a3b-gpu2` | KnowledgeQA | HTTP 404 | ⚠️ **条件失效**——GPU2 是共槽可切换卡（10083），当前显存里是 qwen3.8；切卡后才能用 |

**连带影响（已核实）**：全部 6 个知识库的 **summary 模型都绑定了 `minicpm-v-4.7-35b-a3b-gpu2`**
（当前 404）⇒ 文档摘要/描述生成会失败；embedding 全部 `bge-m3`（健康）。

**建议处置（待用户确认后执行）**：
1. WeKnora 模型管理里**删除或替换** `qwen3.8-27b-ud-q4xl-gpu3`（已死条目，留着只会出错）；
2. 各 KB 的 summary 模型**改绑 `qwen3.8-27b-ud-q4xl-gpu2`**；
3. `minicpm-...gpu2` 可保留作"备用位"，但要明白它只在 121 切卡后生效；
4. 可选：把网关里已有的 `deepseek-flash` / `kimi-k3.1-pro-api` / `deepseek-v4.1-flash-ud-iq3s-gpu3` 注册进 WeKnora
   （实测三者均 200）——按量计费/单槽，适合当"兜底强模型"，注意成本与排队。

**缺失的类型**：无多模态/图片解析模型（各 KB `enable_multimodal=false`，暂无影响）、无 ASR/TTS、无 VLM（`vlm_config` 全空）。要用图片入库/语音问答时才需要补。

## 二、存储（回答"要不要改 MinIO"）

**结论：不需要改，现在也不具备条件。**

- 容器组里**没有 MinIO 容器**（app/frontend×2/nginx/docreader/postgres/neo4j/redis/searxng，实测无 minio）；
  111 上 9000 端口的 `silo` 属于另一套服务（PGSTY 栈），与 WeKnora 无关。
- 全部 KB `storage_provider_config.provider = local`，文件落在 named volume `weknora_data-files`
  （机械盘 `/mnt/data/docker/volumes/`），`.env` 里的 `MINIO_ENDPOINT=minio:9000` 只是默认值，**未启用**。
- 改 MinIO = 先加容器 + 迁移存量文件 + 改配置，收益（水平扩展/多副本）在当前单机量级下不存在。
- 真正要管的是**备份**：`weknora_data-files` 卷已被备份方案覆盖（见 `11-数据安全与备份/`）。

## 五、风险与红线（防遗漏清单）

1. ★ `AUTO_MIGRATE=true`：每次 app 启动都会跑迁移——**升级前先备份**。
2. ★ 6 个 KB 的 summary 模型绑定了一个当前 404 的模型（见第一节，需改绑）。
3. GPU 模型全是"槽位有限、单/少并发"：DeepSeek-V4.1 `--parallel 1`（~7.6 tok/s），批量入库问答会排队——**不要在解析高峰期做实时问答演示**。
4. 121 宿主机重启后 GPU3 上游需手工回载（10084 不在开机回载清单），期间 WeKnora 若绑了它会全挂。
5. LiteLLM 网关配置变更（如 GPU2 换模型）不会自动同步到 WeKnora 的模型注册——**两处要对账**。

## 六、embedding / rerank 选型评估（v2 追加）

问题：要不要把 embedding 从 `bge-m3` 换成 `embeddinggemma-2-GGUF·F16`？**结论：不换，保持 bge-m3。**

| 维度 | bge-m3（现役） | embeddinggemma-2-gpu1 |
|---|---|---|
| 上游 | **111 本机** TEI 容器（GPU），常驻健康 | **121 GPU1** llama.cpp，与 qwen3-reranker-4b、MinerU **共租一卡** |
| 规格 | 1024 维 / 8192 ctx / 多语检索成熟 | ~300M 端侧定位小模型 / 768 维 / 上下文短 |
| 中文长文档（财政报告） | 强项 | 未经我们实测，短上下文对长报告吃亏 |
| 换代成本 | —— | **全部 6 个 KB 向量失效，需整体重算**；`vector_threshold 0.2` 等阈值按新分数分布重调 |

rerank 同理：保持 `bge-reranker-v2-m3`（111 本机 TEI，与 bge-m3 同族配合成熟，`rerank_threshold 0.3` 也是按它的分数尺度调的）；`qwen3-reranker-4b-gpu1` 质量可能更好，但同受 121 GPU1 共租与重启不回载影响，只建议作实验位。

**判据级总结**：embedding/rerank 这类"全库耦合"的组件，换型 = 重算全库 + 重调阈值，收益必须明显大于这个成本才动；上游还多一条"依赖 121 可用性"的减分项。想评 embeddinggemma-2，拿一个新建实验 KB 单独试。

## 七、111 GPU 资源画像（v4 追加，2026-11-04 实测压测）

GTX 1660 SUPER 6G，服务 = TEI embedding（bge-m3，FP16）+ TEI reranker（bge-reranker-v2-m3，FP16）双常驻：

| 状态 | 显存占用 |
|---|---|
| 静息 | **2478 MiB** |
| 负载峰值（批量 16×长文本、并发压测采样） | **3150 MiB** |
| 负载后稳态（CUDA cache 不释放） | ~3022 MiB |
| **空闲下限** | **≈ 3.0 GB** |

**推论（判据级）**：
1. 这张卡是**检索专用资源**（TEI 双进程权重常驻约 2.5G，推理激活仅 ~0.7G，全程稳定）——后来者一律默认 **CPU 化**；真需要 GPU 去 121 排席位。ASR 放 111 走 CPU（SenseVoice CPU 17×实时）正是此判据的应用。
2. ⚠️ TEI 启动参数 `max-batch-tokens=4096`：极端负载实测（16 条 ×8K token × 12 并发）**一半请求超时/失败**——不是显存问题，是单批 token 超限被切成大量子批排队。日常问答（几百 token）碰不到；**批量入库大文档若 embedding 变慢，先查这个参数**（调大它或控制客户端并发/分片大小）。
3. 报显存余量永远按 `nvidia-smi` 的 `free` 列（或 used+free 推算），不信用 `total`——本卡 total 6144 与 used+free 相差 ~400MiB 系统保留。
