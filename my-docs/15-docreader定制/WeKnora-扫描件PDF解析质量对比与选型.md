# 扫描件 PDF 解析质量对比与选型分析

> **问题**（老魏 2026-09-22）：图片版 PDF 的识别结果「**文字准确、排版不行**」。
> **约束**：**不修改 WeKnora 源码**。
> **一句话结论**：排版的天花板由**解析方式**决定，**不是 OCR 参数** —— 纯 OCR 只输出
> 「文本行 + 坐标」，**结构信息在第一步就丢了**；要拿回结构，必须换一个自带版面理解的解析者。
>
> 关联文档：`WeKnora-docreader接入PP-OCRv6方案.md`（我们的 PP-OCRv6 接入方案，本文件是它的质量选型补充）。
> 实测日期：2026-09-22 · 样本：`2025年预算执行等情况审计结果_扫描版.pdf`（38 页 / 27MB / 纯图片）

---

## 一、根因：结构信息在 OCR 阶段就丢了

### 1.1 我们的链路（现状）

```
页面图 → PP-OCRv6（行检测 + 行识别）→ 一堆 (text, bbox) → 几何启发式重组 → markdown
```

**PP-OCRv6 的通用 OCR 产线只做两件事**：检测文本行、识别行内文字。
它**不产出任何区域语义** —— 不知道哪块是标题、哪块是表格、哪块是页眉，
也不知道多栏页面的阅读顺序。

所以我们只能用 bbox 的**几何特征**（行高、x 位置、行距）去**猜**：
- 段落 → 靠「行距 > 行距中位数 × 1.4」+「段首缩进」
- 标题 → 靠「行高比 > 1.15」+「居中」+「不以句读结尾」
- 表格 → **猜不出来**（只有行，没有单元格）

⇒ **天花板就在这**：密集排版（表格页）会让几何判据失效。
实测：第 6 页 **46 行被切成 39 个段落**（几乎一行一段）。

### 1.2 反证实验：调 OCR 参数无效（已实测，推翻了一个假设）

原假设：110 送 1414×2000 的图，但服务端 `text_det_limit_side_len` 默认 **960**
⇒ 检测分辨率损失一半 ⇒ 坐标不准 ⇒ 判据失效。**提高它应该能改善。**

实测结果（同一页，只改该参数）：

| 页 | `det_limit` | 行数 | 均分 | 段落块 | 耗时 |
|---|---|---|---|---|---|
| 1（正文） | 960 | 20 | 0.9922 | 5 | 538 ms |
| 1（正文） | 1536 | 20 | 0.9862 | 5 | 1172 ms |
| 1（正文） | 2048 | 20 | 0.9837 | 6 | 1228 ms |
| 6（密集页） | 960 | 46 | 0.9977 | **39** | 780 ms |
| 6（密集页） | 1536 | 46 | 0.9964 | **39** | 880 ms |
| 6（密集页） | 2048 | 46 | 0.9988 | 40 | 956 ms |

⇒ **行数、段落数几乎不变，置信度略降，耗时翻倍。假设被否定** ✓
**OCR 侧不是瓶颈，960 已足够。**

## 三、VLM 路线实测（细节）

用 WeKnora **实际使用的提示词** `vlmOCRScannedPDFPrompt`（`image_multimodal.go:44-58`），
原文明确要求：*"extract all text **and layout structure** … output in pure Markdown"*、
*"If there are tables, use **Markdown table syntax**"* —— **这正是我们缺的能力**。

### 3.1 同一页（第 6 页，表格密集）的两种输出

**VLM `openbmb/minicpm-o4.5:8b`**（1162 字符 / 14.5 s）：

```markdown
| 序号 | 部门单位名称 | 问题摘要 |
|---|---|---|
| 4 | 工业和信息化部 | 2022年至2025年，所属工业文化发展中心拖欠部本级房租385.48万元，其中2025年117.3万元；<br>至2025年底，所属中国电子学会…涉及项目资金3520万元。<br>… |
```

⇒ **表格结构正确，且单元格内的多行用 `<br>` 合并**（我们做不到）。

**PP-OCRv6**（1131 字符 / 0.8 s）：46 行被切成 **39 个段落块**，无表格，句子被行边界切断。

### 3.2 字准对比：数字集合差异

| 指标 | PP-OCRv6 | VLM(8b) |
|---|---|---|
| 数字个数 | 37 | 36 |
| **VLM 多出（幻觉/误识）** | — | **0 个** ✓ |
| VLM 缺少 | — | 1 个：「**6**」 |

> 唯一的差异是数字「6」—— 而提示词明确要求 *"Ignore headers, footers, and **page numbers**"*，
> 该「6」**疑为页码** ⇒ **属正确遵守指令**，非漏读。

### 3.3 另一个模型的对照（说明模型规模的重要性）

`minicpm-v4.6:1b`（752 M）排版同样好（甚至识别出 `<td rowspan="10">`），但**字准明显下降**：

| 错处 | 1b 输出 | 正确 |
|---|---|---|
| 机构名 | 工业**化**发展中心 | 工业**文化**发展中心 |
| 机构名 | **链管**单位 | **通信管理**局 |
| 数字 | 租金**454**.38 | **254**.38 |
| 数字 | **9304**.8 | **930**.48 |

⇒ **小模型排版可以、字准不可靠**；本场景（审计、金额）**不建议用 1b 级模型**。

## 四、建议

### 4.1 按文档性质分流（推荐）

| 文档性质 | 引擎 | 理由 |
|---|---|---|
| **表格 / 报表密集** | `builtin` + `multimodal: on` + VLM | 排版与表格结构是关键，慢可接受 |
| **纯文字、大批量** | `markitdown`（我们的 PP-OCRv6） | 字准高、快 16 倍、省显存 |

**分流手段**：KB 的解析引擎规则按**文件类型**配，但**模型按知识库配**
⇒ 实务上**按知识库分开建**最干净（老魏已确认过这个形态）。

### 4.2 若想「一份文档兼得两者」

需引入**区域级信息**，只有两条路：
- **② 路线**：110 服务加轻量版面检测（PP-DocLayout，1~2 GB），把区域标签与我们的
  文本行坐标做**匹配**，再重组 ⇒ 能显著改善段落/标题，**表格语义仍需表格识别模块**。
- **改我们的重组算法**（按列分组等）—— **要改代码**，本次约束下不做。

## 五、待验证（现有结论的边界，勿外推）

1. **只测了 1 页**。VLM「0 幻觉」是好信号，但**必须在多页上复核**（建议 10 页，
   统计幻觉率与漏读率）才能作为选型依据。
2. **速度**：14.5 s/页是「模型已加载」的值；冷启动首次约 64 s。
   38 页 ≈ 9 分钟（vs PP-OCRv6 的 34 秒）。
3. **显存竞争**：110 是 **RTX 3060 12 GB**，VLM(≈5 GB) 与 PP-OCRv6(≈1 GB) 不宜并发。
4. **VLM 输出格式遵守度**：8b 模型在表格单元格内用了 `<br>`，而提示词要求
   *"Do NOT include any HTML tags"* ⇒ 轻微不遵守，下游分块需容忍。
5. **`builtin` + VLM 的端到端实测尚未跑**（本次是在 110 上直接调 Ollama 做的对照，
   未经 WeKnora 的 `image_multimodal` 链路）。**建议做一次真实入库验证**。

## 六、版面检测的能力边界与模型选型（2026-09-22 调研）

> 起因：老魏问「版面检测能做到什么程度？哪种最适合我们这种『文字 + 表格』的扫描 PDF（无公式）？」

### 6.1 ★ 先澄清最容易混淆的一点：版面检测 ≠ 表格结构识别

**两个不同的任务、两个不同的模型**：

| | 版面检测（Layout Detection） | 表格结构识别（TSR） |
|---|---|---|
| 输入 | **整页图** | **表格区域图**（由版面检测框出） |
| 输出 | **区域框 + 类别**（23 类） | **单元格行列结构**（HTML / `cell_bbox`） |
| 回答 | 「这块是表格 / 标题 / 正文」 | 「这表几行几列、哪格跨行」 |
| 代表模型 | PP-DocLayout-L/M/S | SLANet / SLANet_plus / SLANeXt |

⇒ **只做版面检测，拿不到表格的行列结构。** 这是本领域最常见的误解。

### 6.2 版面检测能做到什么程度

**能做到**
- 区域框 + **23 类语义标签**：document title / paragraph title / text / page number /
  abstract / toc / references / footnotes / header / footer / algorithm / formula /
  formula number / image / figure caption / **table** / table caption / seal / …
- **阅读顺序**（多栏文档正确排序）
- **可剔除页眉页脚页码**（有专门类别）

**做不到**
- 表格内部行列结构 → 需 **表格结构识别**
- 单元格内容归属 → 需 **单元格检测 + IoU 匹配**
- **段落级细分** → 只到「块」，块内段落仍需几何判据（即我们现有 `LayoutRestructurer` 的活）
- 文字内容 → 需 OCR

**模型规格**（PaddleOCR / PaddleX）：

| 模型 | 骨干 | mAP(0.5) | GPU 推理(ms) 常规/高性能 | 大小 |
|---|---|---|---|---|
| PP-DocLayout-L | RT-DETR-L | **90.4** | 33.59 / **10.39** | 123.8 MB |
| PP-DocLayout-M | PicoDet-L | 75.2 | 13.03 / 4.72 | 22.6 MB |
| PP-DocLayout-S | PicoDet-S | 70.9 | 11.54 / **3.86** | **4.8 MB** |
| PP-DocLayout_plus-L | RT-DETR-L | 83.2（20 类） | 17.23 | 126 MB |
| **PicoDet_layout_1x_table** | PicoDet-1x | **97.5** | 8.02 / 3.09 | **7.4 MB** |

> `PicoDet_layout_1x_table` 值得注意：**只检测表格区域，但 mAP 97.5**（远高于通用版面模型）。
> 只关心「哪里有表格」时它最优；要标题/正文/页眉的语义，仍需完整版面模型。

### 6.3 ★ 针对「文字 + 表格」场景的推荐组合：PaddleOCR 生态（PP-TableMagic）

| 环节 | 模型 | 大小 | 指标 | 备注 |
|---|---|---|---|---|
| 版面检测 | **PP-DocLayout-L** | 123.8 MB | mAP 90.4 | 输出区域类别 |
| 表格分类 | PP-LCNet_x1_0_table_cls | 6.6 MB | Top1 94.2% | 有线/无线判别 |
| **表格结构识别** | **SLANeXt_wired**（或 `_wireless`） | 351 MB | 结构精度 69.65% | **输出 HTML** |
| 表格单元格检测 | RT-DETR-L_wired_table_cell_det | 124 MB | mAP 82.7 | 提供 `cell_bbox` |
| **文字识别** | **PP-OCRv6** | — | — | **已有** ✓ |
| 预处理（建议加） | PP-LCNet_x1_0_doc_ori | **7 MB** | 99.06% | 页面方向 0/90/180/270 |
| 预处理（建议加） | **UVDoc** | 30.3 MB | 0.179 CER | **扫描件弯曲/变形矫正** |

**总模型体积约 650 MB（不含 OCR）⇒ 显存量级 1~2 GB，110 的 6.2 GB 空闲够用。**

**为什么这是最适合我们的**：

1. ★ **与现有 PP-OCRv6 服务同源**（同一套 PaddleOCR / PaddleX）⇒ **只需在现有服务上加模块，
   不引入新框架、不重复部署**；
2. 表格链路成熟：**PP-TableMagic = 表格分类 + 结构识别 + 单元格检测**，直接输出 HTML；
3. ★★ **官方已实现「用单元格几何切分 OCR 结果」** —— `use_ocr_results_with_table_cells`（默认开），
   用 **L1 距离 + IoU** 把 OCR 文本行归属到单元格。
   ⇒ **这正是解耦方案里我们打算手写的那一环，官方版本已有，不必自己造轮子**；
4. 模块可独立开关 ⇒ 关掉公式 / 印章 / 图表，显存按需。

### 6.4 两点提醒

- **`use_table_orientation_classify`（默认开）**：先校正 90/180/270 度旋转的表格再识别；
- **69.65% 是「结构识别」指标**，不等于最终表格可用率。**有线表（我们这类公文表格多为有线）
  表现明显优于无线表** ⇒ 这是选 `SLANeXt_wired` 的理由。

## 七、★ 重新评估 PP-StructureV3（2026-09-22 订正 —— §二 的排除结论过于绝对）

> 起因：老魏指出应重新考虑 PP-StructureV3 并给出官方文档。核对该文档后，
> **§二 中「峰值 17 GB ⇒ 物理装不下」的排除理由不成立，须订正。**

### 7.1 订正：漏了三件事

1. **官方基准里 `default` 配置在 T4 上是 13.6 GB**（17 GB 是更早来源的数字，非此处基准）；
2. 官方提供 **`PP_StructureV3-lightweight` 变体 —— 峰值仅 7.3 GB**（A100 实测）；
3. **子模块可独立开关** —— 其中**公式识别对本场景完全无用**，关掉即可省显存。

官方原文：*"默认配置可能会占用超过 16 GB 的显存…**若需减少显存占用，可参考下文说明修改
配置文件，关闭不必要的功能。**"*

### 7.2 子模块开关（`use_xxx`）与本场景取舍

| 子模块 | 参数 | 产线初始化默认 | 我们的取舍 |
|---|---|---|---|
| 版面区域分析 | `use_region_detection` | True（必选） | ✅ 要 |
| 通用 OCR | `use_general_ocr` | True（必选） | ✅ 要（内含 PP-OCRv6） |
| 文档方向分类 | `use_doc_orientation_classify` | True | ✅ 建议开（扫描件） |
| 文档扭曲矫正 | `use_doc_unwarping` | True | ✅ 建议开（UVDoc） |
| 文本行方向分类 | `use_textline_orientation` | True | ⭕ 可选 |
| 表格识别 | `use_table_recognition` | True | ✅ **要** |
| **公式识别** | `use_formula_recognition` | True | ❌ **关掉**（场景无用） |
| 印章识别 | `use_seal_recognition` | False | ❌ 保持关 |
| 图表识别 | `use_chart_recognition` | False | ❌ 保持关 |

官方另提供预设变体：`-notable`（关表格）/ `-noformula`（关公式）/ **`-lightweight`（全部换最轻模型）**。

### 7.3 显存账（官方基准，供参照）

| 配置 | 硬件 | 峰值设备内存 |
|---|---|---|
| `PP_StructureV3-default` | A100 | 37.4 GB |
| `PP_StructureV3-default` | **T4** | **13.6 GB** |
| `PP_StructureV3-lightweight` | A100 | **7.3 GB** |

110 现状：RTX 3060 **12 GB、空闲 6.2 GB**（Ollama 常驻 4.3 GB）
⇒ **裁剪（去公式）+ lightweight 后有希望，但必须腾显存**（或让 Ollama 按需加载）。
**真实数字必须在 3060 上实测** —— 官方数字来自 A100 / T4，不可直接外推。

### 7.4 为什么这条路「最好」（前两条是决定性的）

1. ★★ **协议天然匹配 ⇒ 零代码接入**：WeKnora 的 `paddleocr_vl` 引擎发的就是
   `POST /layout-parsing`，读的正是 `layoutParsingResults[].markdown.{text,images}`
   —— 与 PP-StructureV3 的服务化接口**完全一致**（这一点早先已核实过）。
2. ★★ **输出即所需**：`parsing_res_list` 直接给出 `block_bbox` / `block_label`
   （`text` / `doc_title` / `paragraph_title` / `table` …）/ `block_content` /
   **`block_order`（阅读顺序）** ⇒ 结构、文字、顺序**一次到位**。
   这比自研「让 LLM 输出标签」可靠得多（专用模型 + 无幻觉）。
3. **一个容器解决全部**：版面 + OCR + 表格 + 预处理（UVDoc / 方向分类）自带，
   不必像 §6.3 那样逐个加模块。

### 7.5 ⚠️ 两个必须处理的坑

1. ★★ **默认只处理前 10 页**！官方原文：*"默认对于超过 10 页的 PDF 或多页 TIFF，**仅处理前 10 页**"*
   ⇒ 必须在产线配置里加：
   ```yaml
   Serving:
     extra:
       max_num_input_imgs: null
   ```
   （我们那份样本是 **38 页** —— 不改这个，后 28 页会被**静默丢弃**，且不会报错。）
2. **镜像 CUDA 版本要匹配 110 的驱动**：官方示例镜像是
   `...paddle:3.1.0-gpu-cuda11.8-cudnn8.9`，而 110 现有 OCR 服务跑在
   `paddle_cuda 12.6 / cudnn 9.5.1` ⇒ 需选定匹配版本后再部署，避免驱动不兼容。

### 7.6 代价（要说清）

- 我们这几轮的 converter 与 36741 服务，在「扫描件 PDF」场景会**冗余**
  （但其「单图 OCR / 多档对比 / 429 退避」仍可服务其它用途）；
- 需腾出 GPU 显存（当前空闲 6.2 GB 不够，要先确认能腾多少）；
- 综合精度仍低于 VLM 端到端（资源低一个量级）；表格结构精度约 69.65%（有线表更好）。

### 7.7 建议的下一步（先验证，再部署）

**先做一次显存可行性验证**（不落正式部署）：在 110 上起容器 → 加载
「去公式 + lightweight」配置 → 用一页样本跑通 → **记录峰值显存与单页耗时**。
数据达标再谈正式部署。**否则可能白折腾一轮。**

## 八、★ 与「组合模型」方案的公平对比（含一处估算订正）

> 起因：老魏认为「PP-StructureV3 不如 §6.3 的组合模型好，主要就是显存问题」。
> 这个方向可能有道理，**但我在 §6.3 给的显存数字是错的，必须先订正**，否则对比不成立。

### 8.1 订正：§6.3 的「显存增量 1~2 GB」严重低估

**错误方法**：我直接拿**模型文件大小**当显存占用（§6.3 的「总模型 ~650 MB ⇒ 显存 1~2 GB」）。
**显存 ≠ 权重体积** —— 还包含激活、buffer、框架与推理引擎开销。

**用本项目已实测的数据校准**：

| 项 | 实测值 |
|---|---|
| PP-OCRv6 medium 权重（`det` 60 MB + `rec` 74 MB） | **134 MB** |
| 该服务实例的显存占用（`nvidia-smi`，不同时刻） | **1068 ~ 2574 MiB** |
| ⇒ **显存 / 权重 比** | **8 ~ 19 倍** |

**据此重算 §6.3 的组合模型**（权重合计 ≈ 643 MB：
PP-DocLayout-L 124 + SLANeXt_wired 351 + 表格分类 6.6 + 单元格检测 124 + UVDoc 30 + doc_ori 7）：

⇒ **显存应在 5 ~ 12 GB 量级，而非 1~2 GB。**

> ⚠️ 该区间是**用比率外推**的估计，不是实测（不同架构的比率不同）；
> 但**量级上「1~2 GB」肯定不成立**。**结论：不能再说"组合模型显存更省"而不加验证。**

### 8.2 重做对比（口径要对齐）

| | 组合模型（自研编排） | PP-StructureV3 |
|---|---|---|
| 显存 | **估 5~12 GB**（须实测） | `lightweight` 7.3 GB（A100，**含公式+图表+印章**） |
| 关掉无用模块后 | 已是最小集 | **应显著下降**（公式/图表正是显存大头嫌疑） |
| 开发成本 | **要写「编排 + 融合」**（见 8.3） | **零**（官方编排） |
| 接入 WeKnora | 改 110 服务 | **零代码**（`paddleocr_vl` 引擎） |

**★ 口径不对等**：7.3 GB 是「lightweight **+ 全模块**」，而我们需要的是**子集**。
⇒ 裁剪后的 PP-StructureV3 **可能落在与组合模型同一区间**，而非高一个量级。

### 8.3 组合模型被忽略的隐性成本：编排与融合要自己写

**PP-StructureV3 的价值不在模型**（组合模型用的就是同一批模型），**而在编排与融合已经做好**：

| 环节 | PP-StructureV3 | 组合模型（自研） |
|---|---|---|
| 区域 ↔ 文本行归属 | 已实现 | **要写**（IoU 匹配） |
| 阅读顺序排序 | 原生 `block_order` | **要写** |
| 表格单元格 ↔ 文本行归属 | `use_ocr_results_with_table_cells`（IoU + L1） | **要写** |
| 多模块调度与 PDF 逐页 | 已实现 | **要写** |

⇒ 自研组合 ≈ 本目录另一份草稿里的「`StructureAnnotator` + `Fuser`」，
**只是把「LLM 判结构」换成「专用模型判结构」**。工作量并不小。

### 8.4 判据（结论）

| 若实测结果 | 则应选 |
|---|---|
| 两者峰值显存差 < ~2 GB | **PP-StructureV3** —— 省一整套编排与融合开发 |
| PP-StructureV3 关模块后仍 ≫ 组合模型，且显存无法腾出 | 组合模型（自研编排换显存） |
| 需要专用版面模型给不了的**语义结构** | 才考虑 LLM 判结构（见解耦方案草稿） |

**⇒ 这个决定应当由一次实测来定，而不是由两份不同口径的估算来定**
（我错了一次：把权重当显存；官方数字来自 A100/T4：不是 3060）。
