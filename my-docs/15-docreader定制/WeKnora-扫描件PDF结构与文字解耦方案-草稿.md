## 零、先例调研：「结构 / 文字分离」在成熟开源框架中有没有现成实现？

**有，而且它正是成熟框架的标准架构。** 2026 年的行业共识是**三层**：

```
① 嵌入文本层（原生 PDF 的 glyph 位置）
② 版面检测  —— 目标检测器标注 region（title/paragraph/table/figure/formula/header/footer）
                并给出阅读顺序
③ 识别层    —— OCR（扫描页）/ 公式识别 / 表格结构识别
```

### 0.1 ★ 最贴合本命题的现成方案：MinerU 的 `pipeline` 后端

| 后端 | 架构 | 精度（OmniDocBench v1.6 Overall） | 显存 |
|---|---|---|---|
| **`pipeline`** | **YOLO 版面检测 + PP-OCRv6 + 表格/公式识别** | **85 ~ 86.5** | **4~6 GB（纯 CPU 亦可）** |
| `vlm` | 1.2B VLM 端到端 | 95.3 | 8 ~ 20 GB |
| `hybrid`（默认） | 混合 | 95.3 | 8 ~ 10 GB |

两个要点：

1. **它的架构就是本命题** —— 版面检测负责结构、OCR 负责文字，**两者分离**；
2. **它的 OCR 就是 PP-OCRv6** —— 与「只用 PP-OCRv6 三体量」的规约**一致**；
   且官方说明 *"pipeline(3.4)：**PP-OCRv6** 后 OCR 精度显著提升"*。

**WeKnora 可零代码接入**：`internal/infrastructure/docparser/mineru_converter.go:53`
的 `backend` 取值 **默认即为 `"pipeline"`**，端点为 `POST {endpoint}/file_parse`（同文件 `:236`）
⇒ 只需在设置里填 `mineru_endpoint`（110 已在 SSRF 白名单中）。

> ★★ **修正本系列文档早先的一处误判**：在 `WeKnora-解析引擎接入机制.md` / `WeKnora-docreader接入PP-OCRv6方案.md`
> 中，我曾以「MinerU 显存 9.7 GB / 峰值 31.6 GB」为由**排除 MinerU** ——
> 那组数字对应的是 **`vlm` / `hybrid` 后端**。**`pipeline` 后端仅需 4~6 GB**，
> 在 110（RTX 3060 12 GB、空闲 6.2 GB）上**可以运行**。该结论需订正。

### 0.2 2026 年的一个反转：主流在「合并」，本命题走的是「解耦」

截至 2026 年中，多数头部工具**把第②③层合并进了单个 VLM**：

- Marker 2 → Surya 2（650M VLM 统一做 layout + OCR + 公式）
- MinerU → `vlm` / `hybrid` 后端（MinerU2.5）
- Docling → `--pipeline vlm`（granite-docling-258M）

行业原文：*"layers two and three have collapsed into a single vision-language model in most of
the leading tools"*；但同文也指出 *"the modular stack has not disappeared, but it is now the
**CPU fallback** rather than the default"*。

⇒ 本命题**不是新发明，而是「模块化解耦」这条路线的延续**。它在 2026 年的定位是
「**低资源 / 稳定 / 可 CPU**」的生产选择 —— **精度低于 VLM 端到端（85 vs 95），但资源低一个量级**。

### 0.3 ★ 需要修正本命题的一处差异：成熟方案用「专用版面模型」，不是通用 LLM

| | 专用版面检测模型（YOLO / RT-DETR / rf-detr） | 通用 LLM 判结构（本草稿 §四 契约） |
|---|---|---|
| 速度 | 单页**几十毫秒** | 估 1~3 s |
| 体积 | **几十 MB** | 数 GB |
| **幻觉** | **结构性不存在** —— 检测器只输出「类别 + 框」，本就不产出文字 | 需靠契约约束 |
| 任务契合度 | 版面检测是它的**专业任务**，且已在 OmniDocBench 上被 benchmark 验证 | 通用能力，靠 prompt 引导 |

⇒ **本草稿契约设计所追求的「无幻觉」，专用检测器天生具备。**
因此优先级应调整为：**能用专用版面模型，就不要用通用 LLM。**

### 0.4 其他可选的开源实现

| 框架 | 结构侧做法 | 备注 |
|---|---|---|
| **Docling**（IBM） | RT-DETR + TableFormer | 许可证宽松、**CPU 可行**、输出 typed document |
| **Surya** | **以版面检测为主任务，OCR 是它的下游消费者** | 解耦最彻底；含阅读顺序与表格 |
| **Marker 2（fast 模式）** | rf-detr 版面检测 | **CPU viable** |
| **PaddleOCR 生态** | PP-Structure（版面）/ TableStructure（表格）/ UniMERNet（公式） | **可单独调用**；与我们现用的 PP-OCRv6 **同源** |

## 一、为什么这个命题成立

上一轮实测暴露了一个**互补关系**：

| 能力 | PP-OCRv6（实测） | 小 VLM `minicpm-v4.6:1b`（实测） |
|---|---|---|
| **文字** | **★ ★ ★** 均分 0.99+，37 个数字 0 错 | **✗** 崩：`工业**化**发展中心`、`**链管**单位`、`**454**.38`(应 254.38) |
| **排版** | **✗** 只给文本行，46 行 → 39 碎片段落 | **★ ★ ★** markdown 表格、`<td rowspan="10">` |

⇒ **两者的短板正好被对方的长板覆盖。**

**关键推论**：上一轮我把「1b 模型字准崩」当作**否决理由** —— 那是**在「单一模型承担两件事」的框架下**才成立。
一旦解耦，**1b 的字准缺陷与我们无关**，而它的排版能力仍可用。

> 这正是本方案最大的价值：**可以用极小体量的模型来获取结构，而不牺牲任何字准。**

## 二、两个可进一步降低成本的洞察

### 2.1 结构判断需要的信息，大多不在像素里

我们的几何重组之所以失败，是因为它**只有几何、没有语义**。而 LLM 要做的判断，
所需要的线索**大量已存在于「行文本 + 行属性」中**：

| 结构线索 | 从哪来 |
|---|---|
| 「一、」「（一）」这类编号 | **行文本** |
| 标题（短、不以句读结尾、居中） | 行文本 + `x` 居中 + 行高 |
| 段首缩进（中文公文缩进 2 字符） | `x1` 偏离左边界 |
| 表格行（多个同行独立块、行高偏小） | 多个 bbox 同行 + 行高 |
| 页眉页脚 / 页码 | `y` 极值 + 行文本模式 |

⇒ **有可能不需要视觉输入**：把「行号 + 归一化坐标 + 行高 + 文本」交给一个**纯文本**模型即可。

**收益**：省掉视觉编码器（显存与时延的大头），110 上现成的 `qwen2.5:7b` 就能用。

### 2.2 输出越短越快

整页 markdown 输出约 1100 字符（VLM 实测 14.5 s/页）。而**只输出标签**时，
输出长度约为 **每行 4 token × 46 行 ≈ 200 token** ⇒ 生成时间应显著低于输出整页文本。

⇒ 推测 **1~3 s/页**（待验证）。这是本方案相对「VLM 直接出 markdown」的第二个优势。

## 三、架构

```
                    ┌─────────────────────────────────────────┐
   页面图 ──┬──────►│  PP-OCRv6（110:36741）                   │
            │       │  输出：N 个 (text, bbox, score)         │
            │       └───────────────┬─────────────────────────┘
            │                       │ 文字 + 坐标（**唯一文字来源**）
            │                       ▼
            │       ┌─────────────────────────────────────────┐
            └──────►│  StructureAnnotator（本方案新增）        │
       （可选视觉）  │  输入：行号 + 归一化坐标 + 行高 + 文本   │
                    │  输出：每行一个「结构标签」              │
                    └───────────────┬─────────────────────────┘
                                    │ 标签（枚举值，**不含任何文字**）
                                    ▼
                    ┌─────────────────────────────────────────┐
                    │  Fuser（融合）                           │
                    │  · 按标签分段 / 定标题层级               │
                    │  · 表格区域 → 几何求列边界 → markdown 表 │
                    │  · 文字一律回填 PP-OCRv6 的原文          │
                    └───────────────┬─────────────────────────┘
                                    ▼
                                 markdown
```

**两条通道的边界**：LLM **只输出标签**，一个字的正文都不采纳；
正文字符**全部**来自 PP-OCRv6。

## 四、接口契约（本方案的核心）

### 4.1 送给 LLM 的输入（文本形态）

```
页 6/38 · 图 1414x2000 · 共 46 行
id | y     | x    | h     | text
0  | 0.048 | 0.217| 0.018 | 中央部门单位2025年度预算执行等情况审计结果
1  | 0.093 | 0.135| 0.018 | 2025年9月至2026年1月，审计署重点审计了39个部门...
```

坐标**归一化到 0~1**（省 token；且与分辨率无关，换 DPI 不影响）。

### 4.2 要求的输出：每行一个标签

```
0:T
1:P
2:P
3:H1
...
```

| 标签 | 含义 | 融合后 |
|---|---|---|
| `T` | 页/文档主标题 | `#` |
| `H1` | 一级小标题（「一、」） | `##` |
| `H2` | 二级小标题（「（一）」） | `###` |
| `S` | 正文**段首** | 起新段 |
| `P` | 正文**续行** | 与上一行**直接相连**（不加空行） |
| `R` | 表格表头行 | 进表格 |
| `D` | 表格数据行 | 进表格 |
| `N` | 页码 / 页眉页脚 | **丢弃** |
| `C` | 图注 / 图表标题 | 普通文本 |

### 4.3 为什么这个契约能**彻底消除幻觉**

| 机制 | 效果 |
|---|---|
| LLM 输出的**文字一律丢弃** | 幻觉**没有进入结果的通路** |
| 只接受**枚举标签** | 非法值可检测 ⇒ 回落 |
| **行号一一对应**（一行一标签） | 不可能漏行 / 多行 / 错位 |
| 覆盖率为 100%（结构上保证） | 无需额外校验 |

⇒ **文字准确率的下界 = PP-OCRv6 的准确率**，即**与现状完全一致**。这是本方案最重要的安全性质。

## 五、融合细节

### 5.1 段落与标题
- `N` → 丢弃（页眉页脚页码不进入正文）
- `T` / `H1` / `H2` → 对应层级的 markdown 标题
- `S` 起新段；`P` 与上一段**直接相连**（避免把断句强化成段落边界 —— 这是现有实现踩过的坑）

### 5.2 表格（关键补足）
LLM **不需要**给出单元格归属，只标出「哪些行属于表格」（`R` / `D`）。
**列边界由几何方法求**：在表格区域内对各行块的 `x1` 做聚类（带容差），得到列边界，
再按 `(行, 列)` 填充成 markdown 表格。

> **为什么交给几何**：表格是**规整对齐**的，x 聚类在这种结构上非常可靠；
> 而让 LLM 输出单元格归属（嵌套结构）既易错又费 token。**各做各擅长的部分。**

### 5.3 跨页续接
沿用现有 `join_pages()` 的逻辑：上一页末尾非句读 ⇒ 与下一页首行相连。
新增判据：若上一页末行为 `D`（表格行）且下一页首行同为 `D` ⇒ 表格续接（暂标记为已知限制，见 §七）。

## 六、容错与降级

| 情形 | 处理 |
|---|---|
| LLM 超时 / 连不上 | 整页回落**现有几何重组**（`LayoutRestructurer`） |
| 输出行数与输入不符 | 缺的行标 `P`（保守）；缺失比例 > 20% ⇒ 整页回落 |
| 出现枚举外标签 | 该行标 `P` |
| 表格区域 < 2 行 | 不当表格，按正文处理 |
| 开关关闭（环境变量） | 全量走现有路径（行为与今天完全一致） |

**原则**：**任何一步失败都退回「现状」，绝不产出比现状更差的结果。**

## 八、待验证（草稿的边界，勿当作结论）

1. **文本+坐标是否足以判断结构**（§2.1）—— 这是本方案最大的未验证假设。
   若不足，需升级到 L2（带视觉）。
2. **小模型的指令跟随能力** —— 1b 级模型能否稳定输出「每行一个标签」的紧凑格式？
   我们已知 1b 擅长排版判断，但**格式遵守度**未测。
3. **速度**（§2.2 的推测）。
4. **表格列聚类的鲁棒性** —— 跨行单元格、无竖线的三线表。
5. **跨页表格/段落的续接**（§5.3）。

### 建议的验证顺序（若后续要实施）
1. 取 **1 页**跑「标签契约」，看格式遵守度与标签质量（低成本，先证伪）
2. 扩到 **10 页**，与现状几何重组**并排对比**（老魏的偏好：可视化并列对比）
3. 达标后再接进 converter，走 `push-reader`（秒级）→ 真实入库对比

## 九、分级实施建议

| 级别 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **L1** | 纯文本小模型给标签（§2.1） | 最低（无视觉编码） | 先试这个 |
| **L2** | VLM 给标签（带图） | 中 | L1 判不准的页 |
| **L3** | 回落：现有几何重组 | 零 | 兜底，永远保留 |

**建议从 L1 起步**：若它够用，则整条路的成本远低于「VLM 直接出 markdown」；
若不够，再上 L2 —— 而**契约（§四）完全不变**，只是换个模型。

> 即：**先定契约，再选模型**。契约是稳定的，模型可以随时替换。

## 十、调研后的选型建议（三条路，按推荐度排序）

| 路线 | 做法 | 结构侧 | 精度 | 显存增量 | 代码改动 |
|---|---|---|---|---|---|
| **甲（推荐）** | 110 部署 **MinerU `pipeline` 后端**；WeKnora 用**自带的 `mineru` 引擎**接入 | DocLayout-YOLO（专用模型） | 85 ~ 86.5 | 需为该服务预留 4~6 GB | **0** |
| **乙** | 给**现有 PP-OCRv6 服务**加一个版面检测模块（PP-DocLayout / DocLayout-YOLO），按区域分派文本行 | 专用模型 | ~85（预期） | **+数十 MB** | 改 110 服务 |
| **丙**（本草稿） | 自研 `StructureAnnotator`：小 LLM 按 §四 契约输出标签 | 通用 LLM | 未验证 | 按需数 GB | 改 `my-docreader/` |

**判断依据**：

- **甲的三个优势**：现成且被 benchmark 验证、**零代码**、其 OCR 本来就是 PP-OCRv6（合规约）。
  **代价要说清**：MinerU 自带 OCR ⇒ **我们这几轮做的 converter、以及那台 36741 服务，在"扫描件 PDF"这件事上会变得冗余**。
  另外 110 显存 6.2 GB 空闲，跑 pipeline 后端后余量很少，不宜再并发其它 GPU 任务。
- **乙的价值**：**复用已有服务与已建成的链路**，显存增量最小（版面模型只有几十 MB）；
  代价是要改 110 服务（但那属于自建服务，不碰 WeKnora）。
- **丙的价值在新场景**：标准版面分析覆盖不到的**语义结构**（例如按业务规则给块打标签、
  区分「问题描述」与「整改情况」这类文档级语义）；而不是替代甲/乙的标准版面分析。

**⇒ 结论**：
**本草稿的「解耦」方向正确，但实现手段应优先用「专用版面检测模型」；**
**只有专用模型覆盖不到的结构语义，才值得交给 LLM。**
