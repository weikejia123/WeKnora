# 用 WeKnora 管一个软件公司的全部知识（多项目 + 领域法规）

> 视角：企业使用者（不是开发者）。目标：把「项目知识 + 项目所处领域的法律法规」管成**一套活的资产**，
> 而不是一堆各自为政的文件夹。
>
> 本文的所有能力判断都落在 WeKnora 的真实数据模型与接口上，依据见文末索引。

---

## 一、先定一个地基判断：法规**绝不能**按项目各存一份

这是整个体系成败的分水岭。先问一个问题：

> 如果「财政领域法规」在每个财政类项目里各存一份，当《预算法》被修订时，你怎么保证
> 12 个项目用的都是新版？你怎么知道哪 3 个项目还在引用旧版？

答案是：**你无法保证**。你会得到一个缓慢腐朽的体系——每个项目里都躺着一份看起来正确、
实则过期或版本不明的法条。这不是存储空间问题（条文很小），而是**版本一致性问题**。

**WeKnora 恰好有一条干净的路支持"引用而不复制"**：

`internal/handler/tenant.go:141 / 829` —— **API Key 可以携带 `knowledge_base_ids` 白名单数组**，
并有 `validateTenantAPIKeyKnowledgeBaseIDs` 校验这些库真实存在且属于该租户。
检索层也是多值（`retriever/postgres/repository.go:170`：`knowledge_base_id IN (...)`）。

⇒ **"某个项目"的检索范围可以配成 `[财政法规基线库, 该项目库]`**，两个库各自唯一、互不复制。
法规修订只改基线库一处，所有项目**立刻**看到新版。

## 二、三层知识模型（每层各有一个"唯一职责"）

| 层 | 放什么 | 谁来承载 | 唯一性 |
|---|---|---|---|
| **L0 企业基准层** | 公司制度、方法论、交付模板、产品/技术文档、项目复盘 | 1~N 个 KB | 全公司一份 |
| **L1 领域法规基线层** | 法律 → 行政法规 → 部门规章 → 规范性文件 → 标准/计价依据 | **按领域各一个 KB** | 每个领域**唯一**、有版本、有生效期 |
| **L2 项目实例层** | 某项目的合同、方案、批复、会议纪要、数据、验收材料 | **一项目一 KB**（或按客户隔离） | 项目内一份 |

**为什么 L1 与 L2 必须分开库**（而不是塞进一个库靠标签区分）：

- KB 是 WeKnora 的**权限边界**（`router/rbac.go:92`：chunks / wiki pages / FAQ / tags
  **继承其所属 KB 的权限**）——把项目材料和公共法规混在一个库里，就没法"全员可读法规、只有项目组能写项目"
- KB **没有层级字段**（`knowledge_bases` 表只有 name/description/tenant_id/各类模型配置）
  ⇒ 库一旦混用，组织只能靠命名，越长越乱

## 三、四个承载物，各司其职（这是 WeKnora 的结构决定的）

| 你要表达的东西 | 用什么 | 依据 |
|---|---|---|
| **知识体系（树）** | **Wiki 目录树**：`wiki_folders`（可先建空文件夹搭骨架）+ `wiki_pages` 的 `parent_slug`/`category_path`/`depth`/`sort_order` | `000061_wiki_page_hierarchy.up.sql` |
| **文档 / 法条原文** | **KB + 文档**（扁平列表） | `knowledge_bases`（无分组字段） |
| **横向维度**（年度/地域/领域/效力等级/状态） | **标签**（多对多） | `knowledge_tags` + `knowledge_tag_relations` |
| **修订与追溯** | **revisions**：分块有 `chunk_revisions`；Wiki 页有 `wiki_page_revisions` | `000075_wiki_page_revisions.up.sql`、`000078_chunk_editing_and_custom_metadata` |

> **关键认知**：KB 是**扁平**的（没有文件夹），所以"体系感"必须由 **Wiki 树 + 命名约定 + 标签**
> 三者共同表达。指望在 KB 里点出一棵目录树是不行的——那是 Wiki 的活。

### 命名约定（因为 KB 扁平，约定就是秩序）

```
KB 命名：  L1-财政法规基线          L2-P2026-南宁财政一体化-实施
           L1-住建法规基线          L2-B2025-某市预算管理一体化-投标
L0 库：    L0-公司制度与交付模板     L0-产品与技术文档
标签（多对多，可叠加）：
           维度:领域   财政 / 住建 / 水利
           维度:效力   法律 / 行政法规 / 部门规章 / 规范性文件 / 标准
           维度:状态   现行 / 已修订 / 已废止
           维度:年度   2025 / 2026
           维度:阶段   投标 / 实施 / 验收
```

`维度:状态` 这一组特别值得认真标——它是"防止拿过期法条当依据"的第一道闸。

## 四、让 Wiki 成为"活的法规网络"（本项目已实测过的机制）

前面我们做过一个实验，机制值得直接复用：**往同一个 KB 里追加政策原文，
KB 级批处理会按归一化标题复用同名页**。

- 原先 `entity/中华人民共和国预算法` 只有 **65 字符**（空壳）
- 导入预算法原文后 → **3548 字符**，`source_refs` 从 1 个变 2 个
- 并**自动产出互链** `[[entity/全国人民代表大会|全国人民代表大会]]`
- 抽验：页面里的"立法沿革"**逐字来自原文题注段**（不是模型脑补）

⇒ 操作含义：**"把被提及的政策原文导入同一 KB"是补实实体页的正解**，比开 GraphRAG 划算得多。
法规库会自己长成一张网：法规 ↔ 机关 ↔ 上位法 ↔ 修订事件。

## 五、权限：三层隔离，各有对应机制

| 隔离需求 | 机制 | 依据 |
|---|---|---|
| 不同客户/公司之间 | **租户（tenant）** | `tenants`、`tenant_members` |
| 公司内部：谁能写基线库、谁只能读 | **租户角色 RBAC**（`owner` / `admin` / `contributor` / `viewer`） | `000043_tenant_rbac.up.sql`（`role` 字段，默认 `contributor`） |
| 项目组之间：只看自己项目 | **KB 级授权**（KB 是权限边界，子资源继承） | `router/rbac.go:92`、`access/kb_transfer.go` |
| 对外集成：只给某项目+对应法规 | **API Key 白名单** `knowledge_base_ids` | `handler/tenant.go:141,829` |
| 留痕 | **审计日志** | `audit_logs` |

一个实用的落地建议：**基线库的写权限收紧到少数人**（法规专员），其余人只读。
否则"公共事实"会被多人各自编辑，慢慢失真——这正是单一事实来源的反面。

## 六、把价值放大到业务流程（这是"最大价值"所在）

知识库如果只是"能搜到文件"，价值有限。真正的价值在**它嵌进业务流程的哪一环**：

| 业务环节 | 用它做什么 | 交付物 |
|---|---|---|
| 投标 / 方案 | 取"适用法规 + 条款原文 + 效力状态"，直接进技术标 | 依据清单（含原文链接） |
| 实施 | 把"条件适用型"审批环节做成合规检查清单，逐项对法规 | 合规自查表 |
| 需求/设计评审 | 每个结论都挂法条依据（结论 → 条款 → 原文 URL） | 可追溯的评审意见 |
| 验收 | 材料生成时直接引法规库，避免"凭记忆写依据" | 验收材料 |
| **法规变更** | 抓取更新 → 定向重导入基线库 → 反查哪些 Wiki 页/项目涉及 | **影响分析清单** |
| 新人培养 | 沿 Wiki 体系树从"领域 → 环节 → 依据"学习 | 学习路径 |

其中**"法规变更闭环"是最高价值、也最容易被忽略的一环**——它让知识库从"仓库"变成"雷达"。

## 七、必须说清的边界（WeKnora 不做的，要外部补）

诚实比完整重要。以下四项**不要指望 WeKnora 自己解决**：

| 缺口 | 说明 | 谁来补 |
|---|---|---|
| **法规时效的自动监控** | 它不抓取外部源、不感知修订，你导入什么它知道什么 | 外部采集服务（如已有政策采集项目）+ 定时重导入 |
| **"这份法规被哪些项目引用"** | 跨库是**检索时组合**，不是入库时建外键 ⇒ 没有引用关系表 | Wiki 互链 / 自定义 metadata / 外部登记表 |
| **审批流与发布流** | 没有工作流引擎（不能"提交→审核→发布"） | 外部流程 + 角色约束（谁有写权限） |
| **字段级权限** | 权限粒度到 **KB**，不到"某文档的某一段" | 用库切分粒度代替（拆库） |

还有一条操作层面的坑，务必记住：**URL 导入 `.html` 结尾的链接会走"文件下载"分支，
文件名改不掉**（`.shtm`/无后缀才走网页解析并自动更名）。
批量导入法规时，**要么统一走 API 显式带 `file_name`，要么别用 `.html` 直链**。

## 八、分阶段落地（每一步都可独立验收）

| 阶段 | 做什么 | 验收标准 |
|---|---|---|
| **1. 领域基线库** | 建 `L1-财政法规基线`，导入法规**原文**；原件落盘 + 登记 `sourceUrl` | 任取一条法规，能回溯到"发文机关的原始页面" |
| **2. 体系树** | 用 Wiki 搭目录骨架（领域 → 环节 → 依据），让实体页自组织 | 打开 Wiki 能看到一棵可导航的树，而非页面列表 |
| **3. 项目库接入** | 建 `L2-<项目>`；项目 API Key 白名单 = `[基线库, 项目库]` | 项目助手问"某环节法定时限"，能同时引到法规原文与项目材料 |
| **4. 权限与留痕** | 基线库写权限收紧；按客户/项目授权；审计 | 非授权角色无法改基线库 |
| **5. 变更闭环** | 定时抓取法规更新 → 定向重导入 → 影响分析 | 法规修订后，能列出受影响的 Wiki 页与项目 |

> **先做 1 和 2，不要一上来就全铺开。** 基线库 + 体系树是地基；项目库再多，
> 也只是在地基上引用同一份权威事实。
