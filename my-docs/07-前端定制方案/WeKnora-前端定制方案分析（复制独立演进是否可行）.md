# 前端定制方案分析：复制一份独立演进，可行吗？

> 提问（2026-09-21）：对现有前端不满意，能否复制当前版本前端、在其上修改，
> 官方原始文件一律不动以持续同步上游；部署后得到两个前端（同 IP、不同端口）？
>
> 本文只做分析，不动任何代码。

---

> **实施更新（2026-09-21，本文写成后已落地）**：实际采用的形态与本节的初步设想不同 ——
> 不是"另起一份独立编排"，而是**把定制前端并入同一个容器组**（老魏的要求：
> "部署时应是一整个容器组"）。落地为：
> - 基底 `docker-compose.yml`（官方，一字不动） + 叠加层 `my-docker/docker-compose.overlay.yml`
> - 新增两个服务：`frontend-wkj`（定制前端）、`nginx`（两个前端的 https/wss 接入层）
> - 两个前端容器都**只绑宿主回环** `14100` / `14102`；对外入口是
>   `https://10.168.1.111:41200/`（官方）与 **`https://10.168.1.111:41280/`**（定制）
>
> 详见 `my-docker/README.md`。下文保留当时的分析（方案对比与风险判断仍然有效）。

## 一、结论

**技术层面可行**，且只需要一个独立编排文件就能做到（不需要动官方前端一个文件）。

**但你描述的策略里有一个必须正视的内在矛盾**：你说的"官方持续保持更新"指的是**后端**，
而复制出去的前端副本**不会自动跟着更新**。于是实际形态是
**「一个会持续变化的后端 + 一个定格在某个时点的前端」**——副本是一个**时间胶囊**。

时间胶囊能撑多久，取决于**后端 API 的变化速度**，而不是前端本身。这是这个方案真正的风险点。

## 二、技术可行性（逐项核对过）

### 2.1 两个前端能共存吗？能

| 关注点 | 核对结果 | 依据 |
|---|---|---|
| 前端能否指向同一后端 | ✅ API 走**相对路径**（`getApiBaseUrl()` 返回 `import.meta.env.BASE_URL`，默认 `/` → 空串） | `frontend/src/utils/api-base.ts` |
| 会不会撞 CORS / Origin | ✅ **不会**。两个前端各自做 `/api` 反代 ⇒ 各自**同源**；且后端认证**全走 `Authorization` / `X-API-Key` 头，不用 cookie** | `internal/router/router.go:112-124`（注释原文）；`frontend/nginx.conf:198` 的 `location /api/` |
| iframe 同源限制会不会碍事 | ✅ 不会。`X-Frame-Options: SAMEORIGIN` 是**防被别的站嵌**，与"两个独立站点"无关 | `internal/router/static.go:46,52-54` |
| 复制范围够不够 | ✅ 够。frontend 构建上下文就是 `./frontend`（自包含），不依赖 `packages/` | `docker-compose.yml` 的 `build.context: ./frontend`；`frontend/package.json` 无 `file:` 引用 |
| 数据是否共享 | ✅ 共享（两个前端 → 同一个 app → 同一个库） | 两个前端反代到同一个 `app` |

### 2.2 副本前端必须独立化的 5 个点（否则会互相覆盖）

| # | 项 | 官方现值 | 副本必须 |
|---|---|---|---|
| 1 | **镜像 tag** | `wechatopenai/weknora-ui:${WEKNORA_VERSION:-latest}` | **换成独立 tag**（如 `weknora-ui-wkj:latest`）★ 否则 `pull`/`build` 会与官方镜像互相覆盖——就是之前修过的"二开镜像被静默覆盖"那类问题 |
| 2 | **container_name** | `WeKnora-frontend`（compose 里写死） | 改名（如 `WeKnora-frontend-wkj`） |
| 3 | **宿主端口** | `${FRONTEND_PORT:-80}`（当前 41200） | 只绑回环 `127.0.0.1:14102`（对外由接入层提供 `https://…:41280`） |
| 4 | **build.context** | `./frontend` | 指向副本目录（如 `./my-frontend`） |
| 5 | **nginx 模板** | `docker-entrypoint.sh` 用 envsubst 注入 `APP_HOST/APP_PORT/APP_SCHEME`、`MAX_FILE_SIZE_MB` 等 | 副本自带一份；副本仍反代到同一个 `app:8080` |

> 做法上与我此前给的 `my-docker/tls/` 同构：**单独一份 compose 文件 + 独立容器名 + 独立镜像 tag**，
> 刻意不并入 `my-docker/docker-compose.yml`（那份要求能与官方逐行比对）。

### 2.3 不需要担心的两件事

- **认证不共享**：token 存在浏览器本地、按 origin 隔离 ⇒ 两个端口**各登录一次**。
  这不是缺陷，是浏览器同源策略的正常结果。
- **前端专属资产重复**：`embed.html` / `weknora-widget.js` / `/r/` 短链等两边都有一份，
  但各自域名独立 ⇒ 无害。

## 三、核心矛盾：副本前端会与后端版本脱钩

这是本方案最需要正视的地方。看一组实测数字（2026-09-20 核对）：

| 事实 | 数值 |
|---|---|
| 线上官方镜像构建于 | `2026-09-03` |
| 上游领先提交数 | **185** |
| 其中 `frontend/` 改动文件 | **1118 个** |
| 其中 `internal/` 改动文件 | 1704 个 |
| 迁移文件 | 63 个 |

⇒ **前后端都在快速变化**。所以"复制一份、自己改、官方后端继续更新"会面临：

| 后端变化类型 | 副本前端的后果 | 可见性 |
|---|---|---|
| 新增接口 | 新功能用不上（副本没有对应界面） | 明显 |
| 接口字段改名/增删 | 调用了已变的接口 ⇒ 报错；或读到 `undefined` **静默错误** | 报错可见，静默错误**难查** |
| 接口语义调整 | 逻辑默默不对 | **最难查** |
| 响应结构变化 | 页面局部空白/异常 | 中等 |

**关键判断**：上游 `frontend/` 与 `internal/` 是**同一批提交里一起改**的
（185 个提交里两边都有大量改动），这说明**前后端契约是被一起演进**的。
副本前端脱离这条演进线，迟早会踩到"后端已经改了、前端还在按旧契约调用"。

**所以"复制并冻结"不是稳定形态；"复制并定期跟上"才是。**

## 四、四个方案对比

| | 方案 | 做法 | 同步上游成本 | 定制自由度 | 适用 |
|---|---|---|---|---|---|
| **A** | **复制 + 定期摘取**（你原案的**正确形态**） | `my-frontend/` 独立目录；把官方 `frontend/` 当 upstream，定期把官方改动 **merge** 进副本 | 每次同步要处理冲突，成本 ∝ 自定义深度 | 高 | 长期维护的"产品化前端" |
| **B** | **薄定制**（不改源码） | 只改运行时 `config.js`（4 项）、i18n 文案、注入额外 CSS/JS | **近乎零**（官方前端可无脑更新） | 低 | 只是视觉/文案不满意 |
| **C** | **独立门户（BFF）** | 保留官方前端当"管理台"，另做自己的界面，**只通过 API 调后端** | **零**（与官方前端彻底解耦） | 高（但界面要自己写） | 不满的是**信息架构/流程**，或要做成对客户交付的产品 |
| **D** | 上游贡献 | 把改动做成 PR 给上游 | 零（跟着官方走） | 取决于是否被接受 | 改动具有通用性 |

### 关于方案 B 的边界（先别高估）

前端**运行时可配置项只有 4 个**（`frontend/public/config.js`）：

```js
window.__RUNTIME_CONFIG__ = {
  MAX_FILE_SIZE_MB: 50,
  MAX_SKILL_BUNDLE_SIZE_MB: 256,
  EMBED_BASE_URL: '',
  DEFAULT_LOCALE: '',          // zh-CN | en-US | ru-RU | ko-KR | ja-JP
};
```

⇒ 不改代码能调的只有"上传上限 / 技能包上限 / embed 域名 / 默认语言"这四项。
其余视觉与结构问题**必须改代码**。

> 另有一条先例值得知道：`frontend/src/utils/api-base.ts` 的注释显示，
> 曾有人通过 **patch**（`plugins/weknora/patches/api-base-baseurl.patch`）把它改造成
> 支持反代到子路径（`/app/weknora/`）。这佐证了「前端被第三方定制」是常见需求，
> 也说明**小改动可以用 patch、大改动才值得 fork**。

### 关于方案 C 的一个关键优势

后端 API 比 UI 稳定得多，且具备自建门户的良好条件：

| 条件 | 现状 |
|---|---|
| 接口风格 | REST `/api/v1/*` |
| 跨域 | `AllowOrigins: ["*"]`（且认证不依赖 cookie，跨域可用） |
| 认证 | `Authorization` / `X-API-Key` 显式头 |
| 编程式接入 | 已有 **MCP** 端点（`mcp_endpoints` 表、`/mcp/:id` 路由） |

⇒ 自己做一个界面挂在同一后端上，**技术门槛比 fork 整个前端低，且永远不会与官方前端冲突**。

## 五、一个容易被忽略的约束：数据不隔离

两个前端共享**同一个后端、同一份数据**。这意味着：

- 好处：不需要同步数据
- 代价：**副本前端里的任何操作，官方前端立刻可见**（反之亦然）

如果这个定制前端是给**客户**看的，那客户与内部员工面对的是同一份数据，**没有隔离**。
要隔离就得两套后端 + 两个库 ⇒ 成本陡增，且与"官方不动"的目标冲突。

⇒ **先确认：这个定制前端是"只给你自己/内部用"，还是要给客户用？**

## 六、如果走方案 A，正确形态是什么

不要"复制后冻结"，而要**做成一个受控的 fork**：

```
my-frontend/                     # 副本（你的定制）
  ...（从官方 frontend/ 复制）

同步机制（每轮上游更新后）：
  1. 记下副本分叉时的官方版本：git rev-parse <分叉点>
  2. 拉取上游，看官方 frontend/ 的改动范围：
       git diff --name-only <分叉点>..<新版本> -- frontend/
  3. 把官方改动合并进副本（逐文件或整体 merge），冲突处按"保留我的定制"处理
  4. 记录本轮"已跟到哪个上游版本"（写进副本 README，避免下次无从对照）
```

**纪律（决定这个方案能活多久）**：

| 纪律 | 原因 |
|---|---|
| 每次升级**后端**时，必须评估前端契约影响 | 脱钩风险的唯一抓手 |
| 副本改动**尽量集中、少而小** | 同步成本 ∝ 自定义深度 |
| 记录"已跟到哪个上游版本" | 否则下次同步无从下手 |
| 独立镜像 tag + 独立容器名 + 独立端口 | 否则与官方互相覆盖 |
| 不改官方 `frontend/` 一个文件 | 保住"官方可无痕同步"这个前提 |

## 七、我的倾向与需要你回答的一个问题

**倾向取决于你「不满意」的性质——这是选方案的分水岭**：

| 你不满意的是 | 建议 |
|---|---|
| 视觉、配色、文案、默认语言 | **B**（成本极低，且官方前端可无脑更新） |
| 局部功能/交互要改，整体认可 | **A**（但要按第六节的纪律做） |
| **信息架构不同**（比如你想按"项目"组织而不是按"知识库"） | **C**（fork 也难改到骨架上） |
| 要做成**对客户交付的产品界面** | **C** |

**一个问题请你定**：你说"不满意"，具体是**样子不对**（视觉/交互），
还是**它不是按你的业务逻辑组织的**（信息架构/流程）？

- 前者 → 方案 B 或 A 就够
- 后者 → 方案 C 更省事，因为 fork 一个别人设计的信息架构，往往比重新做一层界面更累
